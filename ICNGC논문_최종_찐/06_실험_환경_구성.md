실험 중에도 mysqld가 상시 코어 1개를 쓰고 Kubernetes 컨트롤 플레인이 상주합니다.

**대응**: 코어를 고정 배분하고, 런마다 부하를 공변량으로 기록했습니다.

## 2. 소프트웨어 구성

```
                  cluster04 (단일 호스트)
   ┌──────────────────────────────────────────────────┐
   │  코어 0-3       Kafka 3.9.2 (KRaft, 브로커 1대)   │
   │                 토픽 events, 파티션 8             │
   ├──────────────────────────────────────────────────┤
   │  코어 4         Flink JobManager                  │
   ├──────────────────────────────────────────────────┤
   │  코어 5-12      Flink TaskManager × 3             │
   │                 (각 2슬롯, 총 6슬롯 / 잡 병렬도 4) │
   ├──────────────────────────────────────────────────┤
   │  코어 13-15     생성기 (EventGen)                 │
   └──────────────────────────────────────────────────┘
```

| 구성요소 | 버전 / 설정 |
|---|---|
| Flink | 1.20.5, standalone |
| Kafka | 3.9.2, KRaft 모드 (ZooKeeper 없음) |
| 상태 백엔드 | **RocksDB**, 풀 체크포인트 (증분 아님) |
| 체크포인트 저장소 | 로컬 파일시스템 |
| 일관성 | **exactly-once**, **aligned** 체크포인트 |
| 재시작 전략 | fixed-delay, 지연 없음 |
| 하트비트 타임아웃 | 5초 (장애 감지 시간) |
| Java | OpenJDK 17 |

### 왜 TaskManager를 3개 두었나

잡 병렬도가 4인데 슬롯이 6개입니다. **1개를 죽여도 남은 4슬롯으로 즉시 재시작**할
수 있게 하기 위해서입니다. 슬롯이 딱 맞으면 대체 TM이 뜰 때까지 기다려야 해서
복구 시간에 스케줄링 지연이 섞입니다.

## 3. 제약 조건과 그에 따른 설계

### sudo 없음, docker 없음

| 제약 | 확인 |
|---|---|
| `sudo` | 비밀번호 요구 (우리 계정에 권한 없음) |
| docker 소켓 | 접근 거부 |
| `/dev/ipmi` | 없음 (BMC 커널 모듈 미로드) |

**그래서 전부 홈 디렉터리 사용자 프로세스로 구성했습니다.** Flink도 Kafka도
`/opt`나 `/usr/local`이 아니라 `~/icngc2_stream/` 아래에 tarball로 풀어서 돌립니다.

**OS는 하나도 건드리지 않았습니다.** 커널 파라미터, 시스템 서비스, 네트워크 설정
전부 그대로입니다.

### 이게 실험에 미친 영향

| 못 한 것 | 대신 한 것 |
|---|---|
| `tc`/netem으로 링크 지연 조절 | 안 함 (단일 노드라 필요 없어짐) |
| I/O 스케줄러 변경 | 안 함 |
| 페이지 캐시 제어 | `oflag=direct`로 우회 측정만 |
| `dmesg` 전체 접근 | 일부만 (I/O 오류 확인은 가능했음) |

## 5. 실험 자동화 — 무인 46시간 가동

### 체인 방식

각 스윕이 끝나면 다음 스윕이 자동으로 시작됩니다.

```bash
# chain.sh <기다릴_스윕> <다음_설정> <다음_이름>
while ! grep -q "sweep done" "logs/$1.log"; do sleep 60; done
sleep 20
./launch.sh "$2" "$3"
```

**핵심은 "끝나면 만드는 게 아니라, 미리 만들어 대기시킨다"** 는 것입니다.
m12를 기다리는 프로세스가 m8이 시작하기도 전부터 살아 있었습니다.

### 세션 독립성

```
PID     PPID  SID     TTY   CMD
750614     1  750614   ?    python3 sweep.py conf/m6.json
565060     1  565060   ?    chain.sh m8 → m9
```

- **PPID = 1** — 부모가 systemd. SSH나 셸의 자식이 아님
- **TTY = ?** — 제어 터미널 없음 → `SIGHUP` 받을 대상 자체가 없음
- **SID = 자기 PID** — `setsid`로 독립 세션

**실증**: 새벽 1시~아침 7시 30분까지 아무도 접속하지 않은 상태로 37런이 진행됐습니다.

### 재개 가능성

`sweep.py`가 완료한 런을 `logs/<태그>.log.done`에 기록합니다.
중단 후 같은 명령을 다시 실행하면 **남은 런만** 돕니다.

## 7. 환경에서 온 문제 두 가지

### (1) 저장소 드리프트 — 결과의 66%를 날린 원인

31시간 연속 쓰기(누적 11 TB 이상)로 SSD 쓰기 성능이 **288 → 63 MB/s (4.5배)**
떨어졌습니다.

```
09-07 03h   288 MB/s  ████████████████████████████████
09-07 09h   133 MB/s  ███████████████
09-07 15h    75 MB/s  █████████
09-08 00h    62 MB/s  ███████
09-08 07h    63 MB/s  ███████   ← 14시간째 평평
```

`iostat` 확인: `%util 90.6%`, 요청당 `14.7 ms`, 큐 깊이 8.45 → **장치 포화**.
SSD의 SLC 쓰기 캐시 소진으로 추정됩니다.

### (2) 상태 디렉터리 누적 — 중간에 발견해 수정

Flink가 **취소된 잡의 RocksDB 작업 디렉터리를 정리하지 않아** 63개 잡이 지나는
동안 **65 GB**가 쌓였습니다. 체크포인트 소요가 2.1~2.8초에서 4.0~6.6초로 두 배가
됐습니다.

**대응**: 드라이버가 런마다 로컬 상태를 청소하고, 런 종료 시 디스크 사용량을
메타에 기록해 재발을 감지하도록 수정. 73 GB 회수 후 전체 재실행.

**이 문제는 "무장애 대조군의 지연이 장애 런보다 높다"는 말이 안 되는 결과 덕분에
잡았습니다.** 대조군을 넣어둔 게 결정적이었습니다.
