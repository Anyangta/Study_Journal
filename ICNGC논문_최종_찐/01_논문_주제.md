# 01. 논문 주제

## 제목

**Checkpoint Intervals for Latency-Sensitive Stream Processing**
(지연에 민감한 스트림 처리에서의 체크포인트 주기)

## 한 문장

**분산 스트림 처리에서 체크포인트를 얼마나 자주 찍어야 하는가에 대해, 지금 널리
쓰이는 배치/HPC용 공식이 구조적으로 틀렸음을 보이고, 스트리밍에 맞는 식을 유도해
실측으로 검증한 논문.**

## 다루는 문제

Flink 같은 스트림 처리 엔진은 exactly-once를 보장하려고 주기적으로 상태를
체크포인트로 저장합니다. **그 주기 τ를 얼마로 둘 것인가**가 이 논문의 문제입니다.

```
τ가 너무 짧으면  →  체크포인트 자체가 비싸서 평상시 지연이 늘어남
τ가 너무 길면    →  장애 시 되감아야 할 양이 많아 복구가 오래 걸림
                     ↓
              중간 어딘가에 최적점이 있다
```

이 구조는 배치/HPC의 고전 문제와 똑같이 생겼습니다. 그래서 실무에서는 고전 답을
그대로 가져다 씁니다:

```
τ* = √(2 δ M)          δ = 체크포인트 비용, M = 평균 장애 간격
```

## 이 논문이 말하는 것

**그 공식은 스트리밍에 오면 안 됩니다.** 전제가 깨지기 때문입니다.

고전 공식은 두 가지를 가정합니다.

1. 장애가 마지막 체크포인트 이후의 **작업을 파괴한다**
2. 그 작업은 **원래 속도로 재수행된다**

스트리밍에서는 둘 다 틀립니다.

| | 배치 / HPC | 스트리밍 (durable 소스) |
|---|---|---|
| 장애가 하는 일 | 작업을 파괴 | **소스를 되감음** (Kafka 오프셋) |
| 재처리 속도 | 원래 속도 | **남은 용량 (μ−λ)** — 새 입력이 계속 들어오므로 |
| 비용의 모양 | 경과 시간의 **1차** | 백로그 면적 = 경과 시간의 **2차** |
| 최적 주기 | `M^0.5` | `M^0.43 → M^(1/3)` |

**핵심은 재처리가 기계를 독점하지 못한다는 것입니다.** 장애가 난 동안에도,
따라잡는 동안에도 새 데이터는 계속 도착합니다. 그래서 되감은 레코드는 "살아있는
입력을 처리하고 남은 용량"으로만 소화됩니다.

1차 비용을 미분하면 제곱근, 2차 비용을 미분하면 세제곱근이 나옵니다.
**목적함수가 지수 자체를 바꿉니다.**

## 논문이 내놓는 것 (기여)

| # | 기여 |
|---|---|
| **1** | durable 소스를 가진 스트림 처리의 **지연 기준 주기 선택 모델**, 그리고 두 고전 규칙 어느 쪽도 표현하지 못하는 **안정 한계** |
| **2** | 모델의 **모든 항을 실제 Flink/Kafka 배포에서 측정**. 서비스율을 고정한 채 상태 크기만 8배 바꿔, 체크포인트 비용과 복구 비용이 가동률과 독립적으로 움직이도록 설계 |
| **3** | 지수보다 답을 더 크게 움직이는 **측정 결과 두 가지**, 그리고 모델을 스윕 없이 쓸 수 있게 하는 **실무 규칙 `δ ≈ d/2`** |

## 핵심 결과 미리보기

| 결과 | 값 |
|---|---|
| 무보정 장애 비용 예측 | **R² = 0.996** (에피소드 30개) |
| 정상 지연 적합 | **R² = 0.998** |
| 실무 규칙 | **δ ≈ d/2** (δ/d = 0.36~0.61, 저장소 속도 3배 범위) |
| 고전 공식과의 거리 | MTBF 1시간에 **3.1배**, 1일에 **4.9배** |
| 조건 혼합 시 | 면적 적합 R²가 0.982 → **0.016** 으로 붕괴 |
