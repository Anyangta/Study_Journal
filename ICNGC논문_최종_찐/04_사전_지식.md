# 04. 읽기 전에 알아야 할 것 — 개념·용어·수식

논문을 읽기 전에 이것만 알면 됩니다. 위에서부터 순서대로 읽으세요.

---

## 1. 기본 개념

### 스트림 처리 (stream processing)

끝없이 들어오는 데이터를 **도착하는 대로** 처리하는 방식입니다.
배치(batch)가 "쌓아뒀다가 한꺼번에"라면, 스트리밍은 "오는 족족".

- **Flink** — 대표적인 스트림 처리 엔진. 이 논문의 측정 대상
- **Kafka** — 데이터를 순서대로 쌓아두는 로그. 스트림의 **소스** 역할

### 상태 (state)

스트림 처리 잡이 기억하고 있는 것. 예를 들어 "사용자별 누적 클릭 수"를 세는
잡이라면, 사용자마다 카운터를 갖고 있어야 합니다. 그게 상태입니다.

이 논문에서는 **키 20만 개 × 1 KiB = 200 MB** 같은 식으로 상태 크기를 조절합니다.

### 체크포인트 (checkpoint)

**상태를 디스크에 저장해 두는 것.** 장애가 나면 여기서 다시 시작합니다.

```
    ┌─ 체크포인트 ─┐        ┌─ 체크포인트 ─┐
────┴──────────────┴────────┴──────────────┴────→ 시간
     ← τ (주기) →
```

### exactly-once

장애가 나도 **각 레코드가 정확히 한 번만** 처리 결과에 반영되게 하는 보장.
이걸 지키려면 체크포인트가 필수입니다.

### durable 소스 (durable log)

**데이터를 지우지 않고 보관하는 소스.** Kafka가 대표적입니다.

이게 이 논문의 핵심입니다. 장애가 나도 데이터가 사라지지 않으므로,
**되감아서(rewind) 다시 읽으면** 됩니다.

---

## 2. 이 논문의 핵심 용어

### λ (람다) — 도착률 (arrival rate)

초당 몇 개의 레코드가 들어오는가. 예: `λ = 54,462 rec/s`

### μ (뮤) — 서비스율 (service rate)

잡이 최대로 처리할 수 있는 속도. 예: `μ = 108,925 rec/s`

### ρ (로) — 가동률 (utilisation)

```
ρ = λ / μ
```

`ρ = 0.5`면 능력의 절반만 쓰고 있다는 뜻. **여유(headroom)가 `1−ρ`** 입니다.

> **왜 중요한가**: 장애 후 밀린 데이터를 처리하려면 여유 용량이 필요합니다.
> `ρ = 0.8`이면 여유가 5분의 1이라, 백로그를 빼내는 데 쌓일 때보다 5배 오래 걸립니다.

### τ (타우) — 체크포인트 주기

우리가 정하려는 값. 이 논문의 답이 여기에 대한 것입니다.

### δ (델타) — 체크포인트의 등가 스톨 (equivalent stall)

체크포인트 한 번이 파이프라인을 **몇 초 세운 것과 같은 효과**를 내는가.

> **주의 — 이게 논문의 미묘한 부분입니다.** 체크포인트를 뜰 때 파이프라인이
> 실제로 멈추지는 않습니다. 다만 배리어 정렬과 버퍼 대기 때문에 레코드가
> 늦어집니다. 그 효과를 "몇 초 세운 것과 같다"로 환산한 값이 δ입니다.
>
> **δ는 두 가지로 잴 수 있고, 값이 8~18배 다릅니다** (§4.2 참고).

### D — 실효 공백 (effective outage)

장애가 나서 **레코드가 실제로 겪는 공백**. 엔진이 보고하는 "복원 완료" 시각이
아니라, 전속으로 돌아올 때까지 걸린 시간 전체입니다.

> **실측**: Flink 보고 1.2초 vs 레코드가 겪는 4.28초 (**3.6배**)

### M — 평균 장애 간격 (MTBF, mean time between failures)

장애가 평균 몇 초마다 나는가. 예: `M = 55 s`

### μ_d — 배수 속도 (drain rate)

장애 복구 후 **밀린 데이터를 따라잡는 동안**의 실효 처리율.
정상 μ보다 낮습니다 (실측 정상의 93~95%).

## 3. 핵심 수식

### 3.1 백로그와 지연의 관계 — Little의 법칙

```
평균 백로그 = 도착률 × 평균 지연
    L      =    λ    ×     W
```

**이 논문에서 쓰는 방식**: 잡 안에서 레코드마다 `현재시각 − 발신시각`을 재면,
그 레코드 가중 평균이 곧 **백로그 면적**입니다. 그래서 지연을 재면 백로그를
잰 것과 같습니다.

### 3.2 고전 공식 (반박 대상)

```
τ* = √(2 δ M)          ... Young–Odlyzko / Daly
```

**유도 아이디어**: 단위 시간당 낭비 = `δ/τ` (체크포인트) + `τ/(2M)` (장애 시
평균 τ/2만큼의 작업 손실). 미분해서 0으로 두면 위 식.

### 3.3 우리 모델 — 장애 비용

장애 후 되감으면, 살아남은 가장 오래된 레코드는 `a + D`초 전 것입니다.
(`a` = 장애 시점의 체크포인트 경과 시간)

그 백로그 `λ(a+D)`를 여유 `(μ_d − λ)`로 빼내야 하고, 빼내는 동안 레코드는
`μ_d`로 처리됩니다. 그래서 **레코드 가중 초과 지연의 합**은:

```
A = μ_d · λ · E[(a+D)²] / (2 (μ_d − λ))
```

장애는 체크포인트 일정과 무관하므로 `a ~ U(0, τ)`, 따라서

```
E[(a+D)²] = τ²/3 + τD + D²
```

> **여기가 핵심입니다.** `(a+D)`가 **제곱**으로 들어갑니다. 고전 공식에서는
> 1차였습니다. 이 차수 차이가 지수를 0.5에서 1/3로 바꿉니다.

### 3.4 우리 모델 — 전체 비용과 최적 조건

```
Lbar(τ) = ℓ₀ + δ²/(2(1−ρ)τ) + μ_d (τ²/3 + τD + D²) / (2(μ_d − λ) M)
           ↑        ↑                       ↑
        기본 지연  체크포인트 비용          장애 비용
                  (τ가 커지면 감소)        (τ가 커지면 증가)
```

미분해서 0으로 두면 **최적 조건**:

```
(1)   δ² M (1−ρ_d)/(1−ρ) = τ² (2τ/3 + D)          ρ_d = λ/μ_d
```

**두 가지 영역이 있습니다**

| 조건 | 근사 | 지수 |
|---|---|---|
| `D ≪ τ` | `τ* ≈ (1.5 δ² M)^(1/3)` | **세제곱근** |
| `D ≫ τ` | `τ* ≈ δ √(M/D)` | 제곱근 (상수가 고전과 다름) |

실제 배포는 **그 사이(crossover)** 에 있습니다.

### 3.5 낭비 목적함수 (비교용)

용량으로 회계하면:

```
(2)   W(τ) = δ/τ + (D + ρτ/2)/M     →     τ*_waste = √(2δM/ρ)
```

이게 Young–Daly에 가동률 보정을 붙인 형태. 고전형 `√(2δM)`은 `ρ = 1`인 경우입니다.

### 3.6 안정 한계 — 고전 공식이 표현 못 하는 것

주기가 아무리 "최적"이어도, 한 장애가 남긴 백로그를 **다음 장애 전에 못 비우면**
잡에 정상 상태 자체가 없습니다:

```
(3)   λ (τ/2 + D) / (μ_d − λ) + D  <  M
       └──── 백로그 배수 시간 ────┘   └공백┘   └다음 장애까지┘
```

**가동률이 1보다 한참 낮아도 걸립니다.** 실측으로 가동률 50%인데 τ=128초에서
발산했습니다 (예측 한계 82초).

## 4. 실험을 이해하는 데 필요한 개념

### 포화 하한 (saturation floor)

**체크포인트 소요 시간의 약 2배.** 그보다 짧은 주기를 요청해도 실제로는 못 지킵니다.

```
체크포인트가 9초 걸리는데 τ=5초로 설정
    → 실제 주기는 9초 (체크포인트가 끝나야 다음 걸 시작)
    → "5초를 쟀다"고 생각하지만 사실 9초를 잰 것
```

**이 논문에서 실험 실패의 가장 큰 원인이 이것입니다.** 저장소가 느려지면
포화 하한이 올라가는데, τ 격자를 그대로 두면 여러 τ가 전부 같은 값으로 뭉개집니다.

### 드리프트 (drift)

**측정하는 동안 장비 성능이 변하는 것.** 이번 캠페인에서 저장소가 31시간에 걸쳐
288 → 63 MB/s로 4.5배 느려졌습니다 (SSD의 SLC 쓰기 캐시 소진으로 추정).

### 대조런 (control run)

**같은 설정을 스윕 중간중간 반복 실행**해서, 장비가 얼마나 변했는지 사후에
재는 것. 이번에 대조런이 2.23배 차이를 잡아내서 잘못된 값을 논문에 실을 뻔한 걸
막았습니다.

### held-out 검증

**적합에 쓰지 않은 조건**에서 모델이 맞는지 보는 것. 같은 데이터로 적합하고
같은 데이터로 검증하면 순환논증이라, held-out이 훨씬 강한 증거입니다.

## 5. 한 장 요약

```
문제:   체크포인트 주기 τ를 얼마로?

고전:   τ* = √(2δM)          ← 장애가 일을 파괴하고, 원래 속도로 재수행한다고 가정

스트리밍에서 깨지는 이유:
        (1) durable 소스 → 일이 파괴되는 게 아니라 되감김
        (2) 새 입력이 계속 옴 → 재처리는 남은 용량 (μ−λ)로만

결과:   비용이 (a+D)의 1차가 아니라 2차
        → 최적 주기 지수가 0.5가 아니라 0.43→1/3

추가:   고전 공식은 안정 한계도, 주기의 바닥도 표현 못 함
```
