# 05. 실험 방법

## 무엇을 재려 했나

모델에 등장하는 항을 **하나씩 따로** 재는 것이 목표입니다.

```
Lbar(τ) = ℓ₀ + δ²/(2(1−ρ)τ) + μ_d(τ²/3 + τD + D²)/(2(μ_d−λ)M)
          ↑         ↑              ↑        ↑          ↑
         ℓ₀        δ              D       μ_d          λ, μ
```

| 항 | 무엇 | 어떻게 재나 |
|---|---|---|
| **λ** | 도착률 | 생성기가 100ms마다 누적 발신 수를 기록 |
| **μ** | 서비스율 | 백로그를 미리 쌓고 배수 속도 측정 (아래 §3) |
| **ℓ₀** | 기본 지연 | 정상 지연 vs 1/τ 적합의 **절편** |
| **δ** | 등가 스톨 | 같은 적합의 **기울기**에서 역산 |
| **D** | 실효 공백 | 장애 후 나온 가장 오래된 레코드의 나이 − 체크포인트 경과 |
| **μ_d** | 배수 속도 | 복구 중 아직 밀려 있는 구간의 처리율 중앙값 |

---

## 1. 계측 — 왜 엔진 메트릭을 안 썼나

**Flink가 주는 메트릭을 정량 분석에 쓰지 않았습니다.**

| 메트릭 | 문제 |
|---|---|
| `numRecordsOutPerSecond` | **60초 이동평균** |
| `records-lag-max` | **60초 이동평균** |

체크포인트는 2~9초, 재시작은 4~12초 만에 일어납니다. **60초 평균으로는 그 동역학을
아예 볼 수 없습니다.** 실제로 250ms마다 폴링해도 같은 값이 반복되고, 장애 후에도
안 돌아왔습니다.

### 그래서 잡 안에서 직접 쟀습니다

각 레코드에 **발신 시각**을 실어 보내고, 처리하는 연산자가 **500ms마다 서브태스크별로**
이렇게 기록합니다:

```
wall_ms, subtask, 처리한_레코드수, 평균지연, p50, p95, p99, 최대지연
```

지연은 `현재시각 − 발신시각`입니다. Little의 법칙에 의해 **이 요약들의 레코드
가중 평균이 곧 모델이 쓰는 백로그 면적**입니다. 즉 재는 양과 모델의 양이 정확히
같습니다.

Flink REST API는 **잡 상태와 체크포인트 이벤트에만** 4Hz로 사용했습니다.

## 2. 워크로드

```
생성기 (Java)                    잡 (Flink)
──────────────                   ──────────────
정속으로 레코드 발신      →      Kafka      →   keyBy(key)
[발신시각 8B | 키 4B | 패딩]                     ↓
                                            ValueState<byte[]>
                                            (키마다 payload 바이트)
                                                 ↓
                                            spin 루프 (합성 CPU)
                                                 ↓
                                            500ms마다 지연 요약 출력
```

### 조절 손잡이

| 손잡이 | 무엇이 바뀌나 |
|---|---|
| `rate` (λ) | 도착률 |
| `keys` × `payload` | **상태 크기** → δ, D |
| `spin` | 레코드당 CPU → **μ** |
| `ckptInterval` (τ) | 체크포인트 주기 |
| `mtbf` (M) | 장애 주입 간격 |

## 3. μ 캘리브레이션 — 추정이 아니라 실측

모델의 `(μ_d − λ)` 항에 들어가는 값이라 **정확해야** 합니다.

```
1. 토픽 비우기
2. 컨슈머 없이 생성기만 최고 속도로 25~35초 → Kafka에 백로그 쌓임
3. 잡을 earliest 오프셋부터 붙임
4. 밀린 걸 따라잡는 동안의 처리율을 잼   ← 이게 μ
```

**왜 이 방식인가**: 모델에서 μ가 등장하는 자리가 바로 "밀린 백로그를 빼내는
속도"입니다. 그 상황을 그대로 재현해서 재는 게 맞습니다.

## 4. 장애 주입

```
포아송 시점 (최소 간격 40초)에:
  1. 태스크를 실제로 호스팅 중인 TaskManager를 고름
  2. kill -9
  3. 즉시 대체 TaskManager 기동 (다음 장애를 위해)
```

**최소 간격 40초를 둔 이유**: 복구가 끝나기 전에 다음 장애가 나면 두 에피소드가
겹쳐서 독립 표본이 안 됩니다.

### 에피소드마다 기록하는 것

| 항목 | 왜 |
|---|---|
| **마지막 완료 체크포인트의 실제 경과 시간 `a`** | τ/2 평균을 가정하지 않고 **에피소드별로 회귀**할 수 있음 |
| 복원 구간 (엔진 보고) | D의 일부 |
| **피크 지연** | `a + D`와 같음 → D를 역산 |
| catch-up 처리율 | μ_d |
| 초과 백로그 면적 | 장애 비용 |

> **`a`를 실제로 기록하는 게 중요합니다.** 고전 유도는 "평균 τ/2"를 가정하는데,
> 우리는 매 에피소드의 실제 값을 알기 때문에 훨씬 정밀한 회귀가 됩니다.

## 5. 분석에서 제외하는 런 — 기준을 명시하고 따로 보고

| 분류 | 기준 | 왜 제외하나 |
|---|---|---|
| **포화** | 달성 주기 < 체크포인트 소요 × 2 | 체크포인트가 연속으로 돌아 "정상 수준"이 성립하지 않음 |
| **불안정** | 정상 구간 표본 부족 또는 정상 지연 > 5초 | 잡이 정상 상태로 돌아온 적이 없어 "초과"의 기준이 없음 |
| **용량 초과** | 처리량 < λ | 애초에 입력을 못 따라감 (복구 불안정과 다른 현상) |
| **잘림** | 복구가 측정 창을 넘어감 | 면적이 측정값이 아니라 하한값 |

**이 기준을 적용하니 예측 대비 실측 기울기가 0.937 → 1.001로, 무보정 예측 R²가
0.998 → 0.999로 개선됐습니다.** 포함하면 겉보기 일치도가 절반으로 떨어지는데,
그건 **복구한 적 없는 런으로 복구 모델을 검증하는 것**에 대한 경고이기도 합니다.

## 6. 드리프트 대응 — 캠페인 중간에 방법론이 바뀜

m4에서 42런(6시간)을 통째로 날린 뒤 세 가지를 도입했습니다.

### (1) τ 순서 무작위화

**문제**: τ를 작은 것부터 순서대로 돌면, "τ가 클수록 나중에 측정 = 더 느린 장비"가
되어 **드리프트가 τ 의존성으로 위장**됩니다.

**대응**: 블록 안에서 τ 순서를 무작위로 섞음.

### (2) 대조런 삽입

**4런마다 고정 조건(τ=16초)을 반복**합니다. 대조런끼리 비교하면 그 스윕이 도는
동안 장비가 얼마나 변했는지 **사후에 잴 수 있습니다.**

실제로 m6에서 대조런이 **1시간 만에 2.23배 차이**를 잡아냈고, 그 덕분에 R²=0.017짜리
적합을 논문에 실을 뻔한 걸 막았습니다.

### (3) 처리량 조건별로 분리 적합

같은 데이터라도 **처리량 조건이 다른 런을 섞으면 결과가 파괴됩니다.**

| 그룹 | 조건 수 | 면적 적합 R² |
|---|---|---|
| k200k ρ=0.30 | **1개** | **0.982** |
| k200k ρ=0.50 | **3개** | **0.016** |

그래서 분석 코드가 런을 처리량 대역으로 묶은 뒤에만 적합하도록 고쳤습니다.

## 7. 검증 — 수치를 원자료에서 재확인

`verify.py`가 논문에 인용된 모든 수치를 **원자료 CSV에서 다시 계산**해서
논문 텍스트의 값과 비교합니다.

```bash
python3 verify.py          # 전체 검증
python3 verify.py --update # 현재 데이터에 맞는 값 출력
```

**실제로 이 스크립트가 초안의 오류 두 개를 잡아냈습니다** (μ 분산 13.9% → 17%,
상대오차 24.7% → 14.6%). 논문 텍스트를 고치고 데이터를 안 고치면 실패하고,
데이터가 바뀌었는데 텍스트를 안 고쳐도 실패합니다.

## 8. 분석 파이프라인

순서가 중요해서 스크립트로 묶었습니다.

```bash
./refresh.sh
```

```
analyze.py   원자료 런 디렉터리 → summary.json  (런별 요약)
    ↓
drift.py     대조런 산포 확인 + 조건별 δ 적합
    ↓
model.py     δ·D·ℓ₀ 적합, τ* 계산 → fits.json
    ↓
verify.py    논문 수치를 원자료에서 재검증
    ↓
plot.py      그림 생성
```

**순서를 틀리면 이전 스윕의 답이 조용히 나옵니다.** 그래서 개별 실행이 아니라
스크립트 하나로 묶어뒀습니다.
