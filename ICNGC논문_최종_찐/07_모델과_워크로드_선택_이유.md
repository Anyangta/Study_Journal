# 07. 왜 이 모델·이 워크로드인가

## 1. 왜 이 모델(수식)인가

### 왜 "레코드 가중 평균 지연"을 목적함수로 골랐나

**후보가 셋 있었습니다.**

| 후보 | 무엇 | 왜 안 골랐나 / 골랐나 |
|---|---|---|
| 낭비된 작업량 | 재처리에 쓴 CPU | ❌ 배치의 목적함수. 스트리밍 SLA가 계약하는 게 아님 |
| 시간 적분 백로그 | `∫L(t)dt` | △ 물리적으로 자연스럽지만 **재는 양과 다름** |
| **레코드 가중 지연** | `Σ(레코드별 지연)/N` | ✅ **SLA가 쓰는 양이고, 계측이 직접 주는 양** |

**결정적인 이유**: 우리가 잡 안에서 재는 게 레코드마다의 `현재시각 − 발신시각`
입니다. 그 가중 평균이 곧 목적함수면, **재는 양과 모델의 양이 정확히 같습니다.**
변환이 없으니 오차가 안 생깁니다.

> **이 선택을 안 하면 2배 틀립니다.** 처음에 시간 적분 백로그로 유도했더니
> 모델이 실측보다 일관되게 2배 낮았습니다. 원인은 **catch-up 동안 레코드가 λ가
> 아니라 μ_d로 처리되기 때문**입니다. 그래서 레코드 가중 합은 시간 적분의
> `μ_d/λ` 배가 됩니다. 관측된 배율 1.99가 측정된 `μ_d/λ = 1.79`와 맞아떨어져
> 원인을 확인했습니다.

### 왜 `a ~ U(0, τ)`를 가정했나

장애는 체크포인트 일정과 **무관하게** 발생합니다. 그러니 장애가 났을 때
마지막 체크포인트로부터 경과한 시간 `a`는 `[0, τ]`에 균등합니다.

```
E[a] = τ/2          E[a²] = τ²/3
E[(a+D)²] = τ²/3 + τD + D²
```

> **주의**: 고전 유도는 `E[a] = τ/2`만 쓰고 `E[a²]`을 안 씁니다 (비용이 1차라서).
> 우리는 비용이 2차라 `E[a²] = τ²/3`가 필요하고, `(τ/2)² = τ²/4`로 근사하면
> **33% 틀립니다.**

### 왜 δ를 "등가 스톨"이라는 추상으로 뒀나

체크포인트를 뜰 때 파이프라인이 **실제로 멈추지 않습니다.** 비동기로 진행되고,
그동안에도 레코드는 처리됩니다. 그러면 "체크포인트 비용"을 뭐라고 정의해야 하나?

**선택**: "몇 초 세운 것과 같은 효과"로 환산합니다. 그리고 **가정하지 않고 측정**합니다
— 정상 지연을 1/τ에 회귀해서 기울기에서 역산.

**이 선택이 좋았던 이유**: 나중에 δ를 두 가지 방식으로 재보니 **8.8~18.6배** 달랐습니다.
용량으로 재면 0.15~0.22초, 지연으로 재면 1.3~4.2초. 만약 δ를 "체크포인트 소요 시간"
같은 관찰 가능한 값으로 못 박았다면 이 차이를 못 봤을 겁니다.

### 왜 μ_d를 μ와 구분했나

복구 중 처리율이 정상보다 낮을 거라 예상했습니다 (상태 백엔드가 cold). 실측하니
**정상의 93~95%** 였습니다 — 예상보다 작았지만 0은 아니었습니다.

**이 구분을 안 했으면**: 장애 비용을 과소평가했을 겁니다. 여유가 `(μ−λ)`가
아니라 `(μ_d−λ)`인데, ρ=0.5에서 μ가 5%만 줄어도 여유는 10% 줄어듭니다.

## 2. 왜 이 워크로드인가

### 왜 표준 벤치마크(Nexmark 등)를 안 썼나

**후보**: Nexmark, YSB(Yahoo Streaming Benchmark), 실제 데이터셋(NYC 택시 등)

**안 쓴 이유**: 이 논문이 재려는 건 **애플리케이션 성능이 아니라 체크포인트
메커니즘의 비용**입니다. 그러려면 이런 게 필요합니다.

| 필요한 것 | 표준 벤치마크로 되나 |
|---|---|
| 상태 크기를 **정확히 지정** | ❌ 워크로드가 정하는 대로 따라감 |
| 상태 크기를 바꾸면서 **μ를 고정** | ❌ 불가능 |
| 서비스율을 원하는 값에 **고정** | ❌ 불가능 |

**표준 벤치마크를 쓰면 상태 크기와 처리 비용이 함께 움직여서, δ가 커진 게
상태 때문인지 CPU 때문인지 구분할 수 없습니다.**

### 그래서 만든 것 — 손잡이 3개짜리 합성 워크로드

```java
// 키마다 payload 바이트의 상태를 유지
byte[] v = st.value();
if (v == null) v = newPayload(e.key);   // 키 유래 의사난수
// 상태 갱신
st.update(v);
// 합성 CPU 부하
for (int i = 0; i < spin; i++) h = h * 6364136223846793005L + ...;
// 500ms마다 지연 요약 출력
```

| 손잡이 | 무엇을 조절 | 왜 이렇게 |
|---|---|---|
| `keys × payload` | **상태 크기** | δ, D를 움직임 |
| `spin` | **서비스율 μ** | 상태와 **독립적으로** μ 고정 |
| `rate` | 도착률 λ | ρ 설정 |

### 이 설계가 얻어낸 것

**상태 크기를 8배(100 → 800 MB) 바꿔도 μ는 93k~112k rec/s (17%)만 변합니다.**

즉 상태 크기가 **δ와 D만 움직이고 μ·ρ는 건드리지 않습니다.** 교란 변수 없이
한 축만 흔드는 설계입니다. 표준 벤치마크로는 불가능했습니다.

## 3. 워크로드 설계에서 걸렸던 함정 세 개

### (1) payload를 0으로 채우면 안 된다

**처음**: `new byte[payload]` → 전부 0
**문제**: RocksDB의 블록 압축(Snappy)이 그걸 없애버립니다.
**결과**: 200 MB로 설정한 상태가 체크포인트에 **36 MB**로 기록. 체크포인트 소요
0.46초라 δ가 의미 있는 크기가 아니었습니다.

**수정**: 키 유래 의사난수로 채움 → 체크포인트 534~701 MB, 소요 2.1~2.8초로 정상화.

> **교훈**: "상태 크기를 설정했다"와 "저장소가 그 크기를 실제로 쓴다"는 다른 얘기입니다.
> 체크포인트 크기를 반드시 확인하세요.

### (2) 상태는 payload가 아니라 키 개수로 늘려야 한다

**시도**: payload를 1 KiB → 4 KiB로 (상태 4배)
**결과**: **μ가 513 rec/s로 붕괴**

**원인**: 쓰기 대역이 `μ × payload`입니다. payload가 4 KiB면 110k × 4KB = **440 MB/s**
— 저장소가 감당 못 합니다.

**수정**: payload는 1 KiB 고정, **키 개수로만** 상태 조절.
그러면 쓰기 대역이 `μ × 1KB ≈ 110 MB/s`로 묶입니다.

### (3) spin이 없으면 하네스가 병목이 된다

**spin = 0일 때 μ = 1,112,908 rec/s.**

초당 110만 건이면 **생성기와 Kafka가 못 따라갑니다.** 그러면 ρ를 원하는 값에
둘 수가 없습니다 (ρ=0.5를 만들려면 55만 건/초를 발신해야 하는데 생성기 한계가
40만 건/초).

**spin 값 선택**

| spin | μ (rec/s) |
|---|---|
| 0 | 1,112,908 |
| 8,000 | 289,044 |
| **32,000** | **109,623** ← 채택 |
| 100,000 | 39,374 |

`spin = 32000`이면 μ ≈ 110k/s로, ρ=0.8에서도 λ가 88k/s라 생성기(40만/초)와
Kafka가 여유 있게 감당합니다.

> **논문에 쓸 표현**: "레코드당 합성 CPU 부하는 파싱·조인·UDF가 있는 실제
> 파이프라인을 모사하며, 하네스가 아니라 측정 대상이 병목이 되도록 서비스율을
> 원하는 지점에 둔다."

## 4. 왜 RocksDB · 왜 풀 체크포인트 · 왜 aligned인가

| 선택 | 대안 | 왜 이걸로 |
|---|---|---|
| **RocksDB** 상태 백엔드 | HashMap (힙) | 프로덕션 기본값. 큰 상태를 힙 밖에 둘 수 있음 |
| **풀 체크포인트** | 증분(incremental) | δ가 **상태 크기에 비례**하는 깨끗한 관계. 증분은 변경분에 의존해 워크로드 패턴이 섞임 |
| **aligned** | unaligned | 기본값이자 정렬 비용이 δ의 주요 성분. unaligned는 일반성 arm으로 따로 시도 (실패, §11) |
| **로컬 디스크** | 원격(S3/MinIO) | 저장소 지연이라는 변수를 하나 줄임. 원격은 별도 arm으로 검토했으나 기각 (§11) |

### RocksDB 선택의 부수 효과 — 뜻밖의 발견

hashmap 백엔드와 비교하다 발견한 것:

| 백엔드 | 논리 상태 | 실제 체크포인트 |
|---|---|---|
| hashmap | 200 MB | **207 MB** (그대로) |
| RocksDB 풀 | 200 MB | **420~530 MB (2.1~2.6배)** |

RocksDB가 컴팩션 전 SST 파일을 그대로 복사하기 때문입니다.
**δ는 쓰는 바이트에 비례하므로, 백엔드 선택만으로 체크포인트 비용이 2.5배
달라집니다.** 고전 공식의 δ는 이 층위를 표현하지 못합니다.

## 5. 왜 kill -9로 장애를 냈나

**후보**: `kill -9` (프로세스 즉사), `SIGSTOP` (멈춤), 네트워크 분단, 디스크 오류 주입

**선택: `kill -9` TaskManager**

| 이유 | |
|---|---|
| 재현 가능 | 매번 같은 방식 |
| 실제로 일어나는 일 | OOM kill, 하드웨어 장애, 컨테이너 축출 모두 이 형태 |
| root 불필요 | 우리 계정으로 우리 프로세스를 죽이는 것 |
| **측정 대상이 명확** | 감지 → 재시작 → 상태 복원 → 되감기 → 따라잡기 전 과정 |

**한계도 인정합니다**: 느린 노드, 부분 분단, JobManager 손실은 D 분포가 다릅니다.
[11_한계와_반박_가능성.md](11_한계와_반박_가능성.md)에 명시했습니다.

## 6. 왜 데이터셋이 아니라 생성기인가

**"실제 데이터셋을 안 쓰는 게 약점 아닌가?"** — 예상되는 질문입니다.

**답**: 이 논문이 측정하는 건 **데이터의 성질이 아니라 시스템의 성질**입니다.

체크포인트 비용은 **상태 크기와 저장소 대역폭**이 정하지, 데이터의 내용이
정하지 않습니다. 복구 비용은 **되감은 양과 남은 용량**이 정합니다.
실제 택시 데이터를 넣어도 그 관계는 안 바뀝니다.

**대신 생성기가 주는 것**:
- 정확한 도착률 (실측 λ = 54,811 rec/s, 설정값과 오차 0.001%)
- 레코드마다 **발신 시각** → 종단 지연을 정확히 잴 수 있음
- 상태 크기·CPU 부하를 독립적으로 조절

> **논문에 쓸 표현**: "워크로드는 합성이지만 측정 대상은 합성이 아니다 —
> 실제 Flink의 배리어 정렬, 실제 RocksDB 스냅샷, 실제 Kafka 되감기,
> 실제 프로세스 장애를 잰다."
