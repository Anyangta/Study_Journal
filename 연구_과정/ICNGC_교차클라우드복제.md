## 1. 주제가 두 번 무너진 과정

이 연구의 가장 중요한 부분입니다. 심사자가 "왜 이 축을 골랐나"라고 물으면
여기서 답이 나옵니다.

### 1차: "데이터를 옮길까, 질의를 옮길까" (폐기)

처음 잡은 주제는 단일 질의에서 푸시다운과 데이터 전송 중 어느 쪽이 유리한지,
그 교차점을 찾는 것이었습니다. B 사이트의 가용 코어 수를 핵심 변수로 잡았습니다.

**측정으로 반증됨.** 스캔 속도를 재보니 1스레드에서도 이렇게 나왔습니다.

| 워크로드 | 1스레드 | 8스레드 |
|---|---|---|
| 단순 집계 스캔 | 1034 MB/s | 3385 MB/s |
| `LIKE '%...%'` | 695 MB/s | 2838 MB/s |
| `regexp_matches` | 511 MB/s | 2322 MB/s |
| 정규식 추출 + upper | 336 MB/s | 1500 MB/s |

WAN은 100Mbit=12.5 MB/s, 1Gbit=125 MB/s입니다. **가장 무거운 질의를 1코어로
돌려도 CPU가 링크보다 2.7배 빠릅니다.** 교차점이 존재할 수 없습니다.
B의 코어를 1개로 줄여도 0.057초 대 0.832초로 푸시다운이 압승했습니다.

이 표는 논문 §3에 그대로 들어갑니다. 폐기된 가설이 새 주제의 근거가 됐습니다.

### 2차 전환: 반복 질의 횟수 k

전제가 틀린 지점은 "질의 1개"였습니다. 실제로는 같은 데이터를 반복 조회하고,
**푸시다운은 조회할 때마다 egress를 내지만 복제는 한 번만 냅니다.** 그래서
결정 변수는 선택도가 아니라 k(조회 횟수)입니다.

### 3차: "never replicate" 주장 철회 (내 분석 오류)

한때 "10Gbit에서는 지연 기준으로 절대 복제하지 마라(k\*=∞)"라는 결과를 얻어
GitHub에 v1.1.0으로 올렸습니다. **틀렸습니다.**

원인: 복제 플랜의 질의당 **바이트**는 선택도와 무관하지만 질의당 **시간**은
무관하지 않습니다(결과 행을 materialize하는 비용). 그런데 분석 코드가 복제 플랜의
시간을 선택도 전체에 걸쳐 중앙값으로 섞었습니다(89ms). 선택도를 맞추면 σ=0.001에서
로컬 스캔은 4.7ms이고 푸시다운(23.6ms)보다 빠릅니다. k\*는 ∞가 아니라 **174**입니다.

v1.1.1에서 정정했습니다. **커밋 히스토리에 오류와 정정이 모두 남아 있습니다** —
숨기지 않았습니다.

### 교훈

측정은 멀쩡했는데 **분석의 암묵적 가정이 두 번 결과를 뒤집었습니다.**
둘 다 "바이트는 σ와 무관"이라는 참인 명제를 시간으로 잘못 옮긴 것입니다.
비슷한 모델을 세울 때 **양(bytes)과 시간(seconds)의 의존성을 항상 따로 따질 것.**

## 3. 실험 환경과 설계 결정

### 하드웨어

- **cluster03** (사이트 B, 데이터 클라우드): 172.29.54.8, 외부 SSH 5408
- **cluster04** (사이트 A, 분석 클라우드): 172.29.54.9, 외부 SSH 5409
- 둘 다 Intel i9-9900K (물리 8코어 / 논리 16스레드), 베어메탈, `enp1s0f0` 직결 **10 GbE**
- **9명이 함께 쓰는 공용 Kubernetes 노드** (flannel, cni0, docker 다수)
- 내부 sshd는 **2222 포트** (A→B 제어용)

### 설계 결정과 이유

**왜 netem 에뮬레이션인가**
클라우드 계정이 없고 비용을 쓸 수 없었습니다. netem은 시스템 논문의 표준 관행이고,
§5의 클라우드 실측으로 조건이 현실을 감싼다는 걸 보였습니다.

**왜 인터페이스 전체가 아니라 포트 대상 shaping인가**
9명이 쓰는 공용 k8s 노드이기 때문입니다. root qdisc 전체에 netem을 걸면 flannel
VXLAN과 다른 사용자 워크로드까지 느려집니다. `prio` qdisc의 priomap을 전부 0으로
두고, u32 필터로 peer IP + sport(9000, 8800)만 band 1:3의 netem으로 보냈습니다.
매칭 안 된 트래픽은 unshaped band로 흐릅니다. 추가로 `setup/watchdog.sh`가 일정
시간 후 자동 원복하도록 안전장치를 뒀습니다.

**왜 k를 스윕하지 않는가**
각 플랜의 비용이 `c₀ + k·c_q` 구조라, 한 trial에서 K회 반복해 **일회성 비용과
질의당 비용을 분리 측정**하면 모든 k의 곡선이 해석적으로 나옵니다. 덕분에 조건당
43~86 trial로 끝났습니다. 이건 편법이 아니라 비용 구조에서 따라오는 성질입니다.

**왜 MinIO인가**
S3 호환 API를 무료로, 계정 없이, 단일 바이너리로 얻기 위해서입니다.
"교차 클라우드 객체 스토리지"라는 그림이 그대로 성립합니다.

**왜 합성 데이터의 `day` 컬럼이 행 순서와 정렬돼 있는가**
Parquet zone map 가지치기가 동작하는 조건을 만들기 위해서입니다. 로그·시계열
데이터의 자연스러운 성질이기도 합니다. 반대 조건(무상관)은 TPC-H의 `l_shipdate`로
검증했고, 거기서 추정기가 깨지는 것을 정량화했습니다(§5 Result 8).

## 5. 서버에서 겪은 함정 (재현 방지용)

1. **실행 중인 셸 스크립트를 수정하면 안 됨.** bash가 바이트 오프셋으로 읽어가며
   실행하므로 파일이 바뀌면 구문이 깨집니다. `1gbit_50ms` 조건을 한 번 날렸습니다.
2. **Windows에서 scp한 셸 스크립트는 CRLF라 즉시 실패**
   (`/usr/bin/env: 'bash^M': No such file or directory`). 올린 뒤 반드시 CR 제거 후
   `bash -n`으로 문법 확인.
3. **`pkill -f agent_b.py`를 ssh로 실행하면 자기 명령줄까지 매칭해 세션을 죽임.**
   `pkill -f "[a]gent_b.py"`처럼 대괄호를 써야 합니다. 세 번 당했습니다.
4. **DuckDB `.arrow()`는 버전에 따라 `RecordBatchReader`를 반환.** `as_table()`
   헬퍼로 정규화했습니다.
5. **마이크로벤치마크 캘리브레이션이 실제 워크로드로 전이되지 않음.** 집계
   질의로 잰 스캔 속도가 행을 반환하는 플랜의 비용을 13배 과소평가했다
   (0.2초 예측 대 2.6초 실측). DuckDB가 집계에서는 행을 materialize하지 않기 때문.
6. **`SELECT count(*)`로 스캔 속도를 재면 안 됨.** DuckDB가 Parquet footer만 읽고
   답하므로 아무것도 측정되지 않습니다. 모든 컬럼을 건드리는 질의를 써야 합니다.
7. **Git Bash에서 `shutdown /s`는 MSYS 경로 변환에 걸림.** `-s -t` 형태나
   PowerShell을 쓸 것.

# 사이트 A: 전체 조건 자동 실행
DEADLINE=$(date -d "HH:MM" +%s) setsid nohup ./drive_all.sh > drive.log 2>&1 &

## 8. 이 연구에서 나온 음성 결과

논문에도 넣었지만, 여기에 이유까지 적어둡니다.

**B의 코어 수는 무의미했습니다.** 주제 D를 잡을 때 "원격 사이트의 가용 CPU"를
핵심 축으로 삼았는데, 1/2/4/8 스레드에서 k\*가 사실상 평평했습니다(σ=0.05에서
22/17/19/21). DuckDB 1스레드도 링크보다 빨라 원격 CPU가 병목이 되지 않기
때문입니다. **원래 가설이 반증된 것**이고, 그대로 보고했습니다.

**측정 기반 보정항 추가가 오히려 정확도를 낮췄습니다.** 요청당 오버헤드(12.2ms)와
직렬화 속도(259 MB/s)를 모델에 넣었더니 중앙 오차가 나빠졌습니다. 반면 **zone map
가지치기**를 넣으니 23.4% → 12.5%로 절반이 됐습니다. 어떤 항이 중요한지는
측정해봐야 알 수 있다는 사례입니다.
