# 무엇을 하는 논문인가

## 문제

Flink 같은 스트림 처리 엔진은 exactly-once를 보장하려고 주기적으로 상태를
체크포인트로 저장합니다. **그 주기 τ를 얼마로 둘 것인가**가 이 논문의 문제입니다.

- 너무 자주 찍으면 → 체크포인트 자체가 비싸서 평상시 지연이 늘어남
- 너무 드물게 찍으면 → 장애 시 되감아야 할 양이 많아 복구가 오래 걸림

중간에 최적점이 있습니다. 이 구조가 배치/HPC의 고전 문제와 똑같이 생겨서,
사람들은 고전 답을 그대로 가져다 씁니다:

```
τ* = √(2 δ M)        (Young–Odlyzko / Daly)
   δ = 체크포인트 비용,  M = 평균 장애 간격
```

## 주장 — 이 공식은 스트리밍에 오면 안 된다

고전 공식은 두 가지를 가정합니다.

1. 장애가 나면 **마지막 체크포인트 이후의 일이 사라진다**
2. 그 일을 **원래 속도로 다시 한다**

스트리밍에서는 **둘 다 틀립니다.**

| | 배치 / HPC | 스트리밍 (durable 소스) |
|---|---|---|
| 장애가 하는 일 | 일을 파괴 | 소스를 **되감음** (Kafka 오프셋) |
| 재처리 속도 | 원래 속도 | **남은 용량 (μ−λ)** — 새 입력이 계속 들어오므로 |
| 비용의 모양 | 경과 시간의 **1차** | 백로그 곡선의 면적 = 경과 시간의 **2차** |
| 최적 주기 | `M^0.5` | `M^0.43 → M^(1/3)` |

핵심은 **재처리가 기계를 독점하지 못한다**는 것입니다. 장애가 난 동안에도,
따라잡는 동안에도 새 데이터는 계속 도착합니다. 그래서 되감은 레코드는
"살아있는 입력을 처리하고 남은 용량"으로만 소화됩니다.

1차 비용을 미분하면 제곱근, 2차 비용을 미분하면 세제곱근이 나옵니다.
**목적함수가 지수 자체를 바꿉니다.**

## 정확히 말하면 — 세제곱근은 점근값이다

τ\*가 실효 공백 D보다 훨씬 커져야 1/3에 도달합니다. 실측 파라미터로 계산한
국소 지수 `d log τ*/d log M`:

| MTBF | τ\* | 지연 목적함수 | 낭비 목적함수 |
|---|---|---|---|
| 55 초 | 3.6 s | 0.428 | 0.500 |
| 10 분 | 9.4 s | 0.390 | 0.500 |
| 1 시간 | 18.4 s | 0.370 | 0.500 |
| 1 일 | 56.5 s | 0.354 | 0.500 |
| 100 일 | 264 s | 0.337 | 0.500 |

논문은 **"0.43에서 1/3로 접근"** 이라고 씁니다. "세제곱근"이라고만 쓰면
심사자가 잡습니다 (초안에서 이 과장을 발견해 고쳤습니다).

낭비 목적함수는 **정확히 0.500** 이라, 두 답은 M이 커질수록 계속 벌어집니다.

## 유도한 식

기호: λ=도착률, μ=서비스율, ρ=λ/μ, a=장애 시점의 체크포인트 경과 시간,
D=**실효 공백**, μ_d=복구 중 처리율. 장애는 체크포인트 일정과 무관하므로
a ~ U(0, τ), E[(a+D)²] = τ²/3 + τD + D².

목적함수는 **레코드가 겪는 평균 종단 지연** (지연 SLA가 쓰는 양). catch-up
동안 레코드는 λ가 아니라 μ_d로 처리되므로, 레코드 가중 합은 백로그
시간적분의 **μ_d/λ 배**입니다.

```
Lbar(τ) = ℓ₀ + δ²/(2(1−ρ)τ) + μ_d (τ²/3 + τD + D²) / (2(μ_d − λ) M)
```

미분해서 0으로 두면:

```
(1)   δ² M (1−ρ_d)/(1−ρ) = τ² (2τ/3 + D)
```

낭비(처리량) 목적함수로 회계하면:

```
(2)   W(τ) = δ/τ + (D + ρτ/2)/M   →   τ*_waste = √(2δM/ρ)
```

(2)가 Young–Daly에 가동률 보정을 붙인 형태이고, 고전형 `√(2δM)`은 ρ=1인 경우입니다.

## 고전 공식이 표현조차 못 하는 것 — 안정 한계

주기가 "최적"이어도, 한 장애가 남긴 백로그를 다음 장애 전에 못 비우면
잡에는 정상 상태 자체가 없습니다:

```
(3)   λ (τ/2 + D) / (μ_d − λ) + D  <  M
```

**이 한계는 가동률이 1보다 한참 낮아도 걸립니다.** 실측으로 가동률 50%인데도
τ=128초에서 발산했습니다. 고전 공식에는 이 조건을 표현할 항이 아예 없는데,
√M로 자라는 주기를 추천하면서 (3)을 넘는 걸 막을 장치가 없습니다.

## 논문의 기여 세 가지

1. durable 소스를 가진 스트림 처리의 **지연 기준 주기 선택 모델**과,
   두 고전 규칙 어느 쪽도 표현하지 못하는 **안정 한계**
2. 그 모델의 **모든 항을 실제 Flink/Kafka 배포에서 측정**.
   서비스율을 고정한 채 상태 크기만 8배 바꿔서, 체크포인트 비용과 복구 비용이
   가동률과 독립적으로 움직이도록 설계
3. 지수보다 답을 더 크게 움직이는 **측정 결과 두 가지** —
   체크포인트가 용량으로 치르는 값과 지연으로 치르는 값의 차이,
   그리고 엔진이 보고하는 공백과 레코드가 겪는 공백의 차이
