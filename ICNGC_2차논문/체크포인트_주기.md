## 2026-09-06 — 고부하(ρ=0.8) arm 결과, 가동률 천장 발견 (v0.3.1)

### 한 일

ρ=0.8 (λ=87,698) τ 스윕 7런 완료. ρ=0.5와 질적으로 다른 영역임이 확인됨.

|---|---|---|---|---|

**발견 1 — 가동률 천장.** τ=2,4에서는 아예 λ를 못 따라감(처리량 < λ). τ≥8에서는
따라가지만 장애 복구가 다음 장애를 못 앞질러 영구 지연 상태. **최적점은 여전히
존재하나(τ≈8s) 그 최적점조차 지연 21초로 쓸 수 없음.** 이 구성의 가동률 천장은
0.5와 0.8 사이.

**발견 2 — 지속 가능 처리율이 τ의 함수.** 이 런들은 포화 상태이므로 처리량이 곧
주기별 최대 지속 처리율: τ=2에서 83.5k → τ=128에서 102.8k, **23% 차이**.
즉 "가동률 ρ"는 τ를 명시하지 않으면 정의되지 않는다. 드레인 캘리브레이션의
μ=108.9k는 (빈 상태에서 시작하는 드레인의 중앙값이라) 다소 낙관적인 값.

  후자는 정상 구간 자체가 없음. ρ=0.8에서 3런 중 2런이 overloaded.
- 런 메타(`_mtbf_run`, `_rho_cfg`, `_mu_cfg`)를 요약에 영구 기록.

### 확정된 네 가지 발견

1. **주기에 바닥이 있다.** 체크포인트 소요(2.1~2.8s)의 약 2배 아래로는 비용이
   1/τ로 줄지 않고 되레 늘어난다(τ=2,4에서 정상 지연 622/696ms vs τ=8에서 265ms).
   고전 규칙은 이 바닥을 표현할 항이 없다.
2. **체크포인트는 없애는 처리량보다 5.8배 많은 레코드를 지연시킨다.**
   용량 기준 δ=0.221s, 지연 기준 δ=1.277s. δ가 제곱으로 들어가므로 용량 기준
   값을 지연 목적함수에 넣으면 체크포인트 항을 **34배 과소평가**한다.
3. **엔진이 보고하는 복원 시간은 실제 공백의 1/3.** Flink 보고 1.25s vs 레코드가
   겪는 실효 공백 4.11s(에피소드 36회, 표준편차 0.5s). 차이는 태스크 스케줄링 +
   600MB RocksDB 재개 + Kafka fetch 재확립. 장애 항을 약 10배 과소평가하게 된다.
4. **임계 주기를 넘으면 아예 못 따라잡는다.** τ=128s에서 평균 지연 126초로 발산.
   용량 문제가 아님(가동률 50%). 조건 `λ(τ/2+D)/(μ_d−λ) + D < M` 으로 계산한
   한계 72s에 대해 τ=64 안정 / τ=128 불안정 — 정확히 그 사이.

### 방법론적으로 중요했던 교정

- 목적함수를 **레코드 가중 평균 지연**으로 다시 유도. catch-up 중 레코드는 λ가
  아니라 μ_d로 처리되므로 레코드 가중 초과분 = 백로그 면적 × μ_d/λ.
  이 보정 전에는 모델이 실측보다 2배 낮았음 (관측 1.99배 = μ_d/λ 1.79와 일치).
  → `A = μ_d·λ·E[(a+D)²] / (2(μ_d−λ))`, 최적 조건
  `δ²M(1−ρ_d)/(1−ρ) = τ²(2τ/3 + D)`, D≪τ에서 τ\* ≈ (1.5δ²M)^(1/3).
- 무보정 예측 검증: peak 지연과 배수 속도만으로 에피소드 비용 예측 →
  **R² = 0.998, 중앙 배율 1.14, 중앙 상대오차 24.7%** (2자릿수 범위에 걸쳐).
- 포화(τ < 2×체크포인트 소요)·불안정 런은 명시적 기준으로 회귀에서 제외하고
  별도 보고.

## 2026-09-06 — 캘리브레이션 완료, 본 스윕 가동 (v0.2.0)

### 한 일

- **서비스율(μ) 캘리브레이션 확립**. 백로그를 미리 쌓아두고(no consumer) 잡을
  earliest부터 붙여 배수 속도를 재는 방식 → 모델의 (μ−λ) 항에 그대로 들어가는 값.
- **spin(레코드당 합성 CPU 작업)이 μ 제어 손잡이**로 확정:

  | spin | μ (rec/s) |
  |---|---|
  | 0 | 1,112,908 |
  | 8,000 | 289,044 |
  | 32,000 | 109,623 |
  | 100,000 | 39,374 |

  spin=0이면 μ가 1.1M/s라 생성기·Kafka가 못 따라가 ρ 제어가 불가능.
  **spin=32000 (μ≈110k/s)** 을 운용점으로 채택.
- **상태 크기를 payload가 아니라 키 개수로 늘리는 것이 정답**:
  payload=4096(800MB)은 쓰기 증폭(μ×4KB=440MB/s)으로 **μ가 513/s로 붕괴**.
  키 개수로 늘리면 쓰기 대역이 μ×1KB로 묶여 안정적.

  | 상태 (payload 1024) | μ (rec/s) |
  |---|---|
  | 100k keys ≈ 100MB | 112,480 |
  | 200k keys ≈ 200MB | 109,623 |
  | 400k keys ≈ 400MB | 104,299 |
  | 800k keys ≈ 800MB | 96,858 |

  → **상태를 8배 바꿔도 μ는 14%만 변함.** δ·D만 움직이고 μ·ρ는 고정되는
  깨끗한 실험 설계 확보.
- **본 스윕 가동** (48런, 약 7.8h): τ ∈ {2,4,8,16,32,64}s ×
  {상태 100/200/400/800MB, ρ 0.5/0.8, MTBF 0/55/150s}
- 에피소드마다 **실제 체크포인트 경과 시간(a)** 을 기록하도록 분석기 개선 →
  τ/2 평균 가정 없이 개별 회귀 가능.

### 참고할 맥락 / 결정 사항

- 최적 조건 정밀화: 장애 시점의 체크포인트 경과 a ~ U(0,τ)이므로
  E[(a+D)²] = τ²/3 + τD + D² (기존 (τ/2+D)² 근사보다 정확).
  → **δ²M = ρτ²(2τ/3 + D)**, D≪τ에서 **τ\* = (1.5·δ²M/ρ)^(1/3)**
- 낭비 목적함수: W(τ)=δ/τ+(D+ρτ/2)/M → τ\*=√(2δM/ρ) (Young/Daly 형태)
- 실측 계측은 Flink 메트릭이 아니라 **잡 내부 500ms 지연 요약**이 1차 소스.
  Flink의 numRecordsOutPerSecond·records-lag-max는 60초 이동평균이라 사용 불가.
- 서버는 공용이라 mysqld가 상시 코어 1개를 씀(≈91% CPU) + k8s 상주. taskset으로
  Kafka 0-3 / JM 4 / TM 5-12 / 생성기 13-15로 격리하고, 런마다 loadavg를 공변량으로
  기록 중.

### 참고할 맥락 / 결정 사항

- **유도한 모델** (지연/lag 목적함수):
  - 체크포인트 1회 = 실효 스톨 δ초 → lag 면적 λδ²/(2(1−ρ)), 단위시간당 ÷τ
  - 장애 1회 = 다운타임 D + 되감기 λ(τ/2+D) 백로그를 (μ−λ)로 배수
  - `L̄(τ) = ℓ₀ + δ²/(2(1−ρ)τ) + [D²/2 + λ(τ/2+D)²/(2(μ−λ))]/M`
  - 최적 조건: **ρ·τ²(τ/2 + D) = δ²·M** → (1−ρ)는 소거됨
    - D ≪ τ/2 이면 **τ\* = (2δ²M/ρ)^(1/3)** — **세제곱근**
    - D ≫ τ/2 이면 τ\* = δ√(M/(ρD)) — 제곱근
- **처리량 낭비 목적함수**로 바꾸면: `W(τ) = δ/τ + (D + ρτ/2)/M` →
  **τ\* = √(2δM/ρ)** — 고전 Young/Daly 형태 그대로.
- **논문 한 줄**: *같은 시스템, 같은 장애율인데 무엇을 최적화하느냐가 최적
  체크포인트 주기의 스케일링 지수 자체를 바꾼다 (√M vs M^(1/3)).* M이 커질수록
  두 답이 벌어지므로, 신뢰성 높은 클러스터일수록 고전 규칙이 지연 민감 스트리밍에
  더 크게 틀린다.
- 효율적 측정 전략: M별로 전부 돌리지 않고 **steady(τ)** 와 **장애 1회당 lag
  면적 area(τ)** 를 분리 측정해 `L̄(τ;M) = steady(τ) + area(τ)/M` 로 합성.
  M 몇 점만 end-to-end로 검증.

### 참고할 맥락 / 결정 사항

- **핵심 가설**: 배치용 Young/Daly 최적 주기 τ*=√(2δM)는 스트리밍에 맞지 않는다.
  스트리밍은 소스(Kafka)가 durable해서 "잃은 일"을 재계산하는 게 아니라 **재생(replay)**
  하고, 그 재생분은 여유 처리량 (μ−λ)로만 소화된다. 따라서 최적 주기가
  **가동률 ρ=λ/μ (여유 headroom)** 에 의존한다 — Daly 식에는 그 항이 아예 없다.
- lag-area(지연 면적) 목적함수에서 예측: τ* ∝ [a·M·(μ−λ)/λ²]^(1/3) — **세제곱근**.
  처리량 손실 목적함수로 바꾸면 제곱근으로 돌아감 → "무엇을 최적화하느냐가 지수를
  바꾼다". 1차 논문의 방법론(손익분기 + 비용모델 + held-out 검증)과 같은 틀.
- 서버: cluster04 = 172.29.54.9, 외부 SSH 5409, i9-9900K 8코어/16스레드, 베어메탈.
  cluster03 = 172.29.54.8, 외부 5408 (1차 논문 때부터 응답 불능).
