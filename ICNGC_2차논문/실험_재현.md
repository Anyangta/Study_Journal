## 3. 처음부터 다시 세우기

```bash
cd ~/icngc2_stream
./cluster.sh kafka-start          # KRaft 브로커
./cluster.sh topic-reset 8        # events 토픽 8파티션
./cluster.sh flink-start 3        # JM 1 + TM 3 (슬롯 6)
./cluster.sh status

# 컴파일 (maven 없음 — Flink lib 대상 javac)
javac -nowarn -cp "flink-1.20.5/lib/*" -d classes CkptJob.java && jar cf ckptjob.jar -C classes .
javac -nowarn -cp "lib/kafka-clients-3.9.1.jar" -d gclasses EventGen.java && jar cf eventgen.jar -C gclasses .
```

**주의 (실제로 걸렸던 함정)**

1. `EventGen`은 `kafka_2.13-3.9.2/libs/*` 전체를 클래스패스에 넣어야 합니다
   (`kafka-clients` 단독이면 slf4j 없음으로 죽음).
2. 잡 파라미터는 `JVM_ARGS="-Dxxx=..."` 로 `flink run`에 전달합니다
   (main()이 클라이언트 JVM에서 돌기 때문).
3. `flink-connector-kafka` + `kafka-clients` jar는 `flink-1.20.5/lib/`에 넣어야
   TaskManager에서도 보입니다.
4. 백그라운드 실행은 반드시 `setsid nohup ... < /dev/null &`. ssh 파이프를 물면
   호출자가 블로킹됩니다.
5. `pgrep -f calib.py` 같은 패턴은 **자기 자신을 매칭**합니다. `pgrep -f "[c]alib.py"`.

## 4. 실험 실행

```bash
python3 calib.py conf/calib4.json results/calib4.json     # μ 측정
python3 mkcfg.py conf/spec_m2.json conf/m2.json           # 스윕 설정 생성
./launch.sh conf/m2.json m2                               # detached 실행
tail -f logs/m2.log
```

- `sweep.py`는 `logs/<tag>.log.done`에 완료 런을 기록하므로 **중단 후 같은 명령으로
  재개**하면 남은 런만 돕니다.
- 런 1회 ≈ warmup 75s + measure 480s + 정리 55s ≈ 9.5분.

## 4b. 공용 장비 드리프트 — 스윕을 짜기 전에 반드시 읽을 것

cluster04는 mysqld·etcd·kube-apiserver가 같이 도는 **공용 장비**입니다.
체크포인트 **쓰기 처리량이 하루 안에 4배 흔들립니다** (새벽 268 MB/s → 오후 66 MB/s,
체크포인트 크기는 그대로). 2026-09-07에 JobManager 로그의 체크포인트 6127개를 파싱해
확인했습니다.

`mkcfg.py`가 만드는 스윕은 `c2 → c4 → … → c128`, 즉 **τ가 커지는 순서로 시간 순차
실행**되기 때문에, 이 드리프트가 적합하려는 곡선을 그대로 휘게 만듭니다. 오후엔
체크포인트 소요가 7~9초라 τ=2/4/8s 구간이 전부 포화돼 1/τ 신호 자체가 사라집니다.

**그래서 새 스윕은 `mkcfg.py` 대신 `mkcfg_drift.py`를 쓰세요.**

```bash
python3 mkcfg_drift.py conf/spec_m6.json conf/m6.json   # 블록 안 τ 무작위 + 대조런
./launch.sh conf/m6.json m6
```

spec의 블록마다 `"shuffle": true`, `"control_ckpt": 16000`, `"control_every": 4`를
주면 τ 순서를 섞고 고정 τ 대조런을 4런마다 끼워 넣습니다. 대조런끼리 비교하면
그 스윕이 도는 동안 장비가 얼마나 느려졌는지 사후에 잴 수 있습니다.

그리고 **가장 중요한 arm은 00~06시에 배정**하세요. 그 시간대가 200~270 MB/s로
가장 조용하고 안정적입니다.

측정 조건을 확인할 때:

```bash
python3 drift.py table k200k          # 런별 시각·τ·정상지연·ckdur·MB/s
python3 drift.py fit k200k _r50_ _m0_ # 그 부분집합만으로 정상 항 재적합
```

**δ(정상 항)는 무장애(mtbf=0) 런으로 재세요.** M=55s 장애 런은 55초마다 장애 +
복구 8초 + 체크포인트 5~9초라 "정상 구간" 표본이 거의 남지 않습니다.
그리고 창 안에 체크포인트가 5개 미만인 런은 배제하세요 — 그건 정상 수준이 아니라
그때 낀 스파이크입니다.

## 5. 분석

```bash
python3 analyze.py            # results/summary.json, summary.csv
python3 model.py              # results/fits.json + τ* 표
python3 plot.py               # figs/fig1..fig4 (pdf+png)
python3 verify.py             # 논문 수치 재검증
python3 verify.py --update    # 현재 데이터에 맞는 QUOTED 블록 출력
```

**스윕이 끝나면 `./refresh.sh` 한 줄이면 됩니다.** 위 순서대로 전부 돌립니다.

```bash
./refresh.sh            # 전체 (조용히)
./refresh.sh -v         # 각 도구의 출력을 다 보여줌
./refresh.sh --quick    # analyze.py 건너뜀 (summary.json이 최신일 때)
```

> **순서가 중요합니다.** `analyze.py`가 원자료에서 `summary.json`을 다시 만들고,
> `model.py`가 거기서 적합하고, `plot.py`가 그 적합에서 그리고, `verify.py`가
> 그 셋에서 논문 수치를 재유도합니다. 순서를 틀리면 **이전 스윕의 답이 조용히
> 나옵니다.**

**2026-09-07에 바꾼 것 (되돌리지 말 것)**

- `model.py` — 정상 항(δ)을 **무장애 런이 3개 이상이면 그것만으로** 적합.
  또 `n_ckpt < 5`인 런은 배제(`MIN_CKPT`). 진단 줄에 `thin=`과 `src=`가 찍힘.
  이 두 줄로 기준 arm의 R²가 0.008 → 0.863, k100k가 0.110 → 0.979로 회복됐음.
- `plot.py` — fig4가 `0.42 ≤ ρ ≤ 0.62`로 하드코딩돼 있었음. **상태 크기를 가장
  많이 커버하는 ρ를 자동으로 고르도록** 변경. ρ=0.50에서는 k400k·k800k가
  체크포인트만으로 불안정해 2점밖에 안 나오므로, 4점 스케일링은 ρ=0.30에서
  측정한다. 실행 시 `fig4: rho=0.3, state sizes 100k, 200k, 400k, 800k`처럼 찍힘.

## 6. 고정된 실험 파라미터 (바꾸면 결과가 안 맞음)

| 항목 | 값 | 이유 |
|---|---|---|
| spin | 32000 | μ를 ≈110k rec/s로 고정. spin=0이면 μ=1.1M/s라 생성기가 병목 |
| payload | 1024 B, 키 유래 의사난수 | 0으로 채우면 RocksDB 압축에 먹혀 상태 크기가 안 나옴 |
| 상태 크기 | 키 개수로 조절 (100k~800k) | payload로 키우면 쓰기 대역(μ×payload)이 터져 μ가 붕괴 |
| par | 4 (슬롯 6 중) | 장애 후 즉시 재시작할 여유 슬롯 확보 |
| heartbeat.timeout | 5000 ms | 감지 시간 상수 |
| 코어 고정 | Kafka 0-3 / JM 4 / TM 5-12 / gen 13-15 | 공용 서버라 간섭 격리 |
| 계측 | 잡 내부 500ms 지연 요약 | Flink 메트릭은 60초 이동평균이라 사용 불가 |
