## ② 반드시 들어갈 수치

### A. Setup

| 항목 | 값 |
|---|---|
| 환경 | Flink 1.20.5, Kafka 3.9.2 (KRaft), RocksDB full·aligned·exactly-once |
| 노드 | 8코어 × 2 (1노드 / 2노드) |
| 상태 크기 | 약 100 / 200 / 400 MB |
| ρ | 0.30 ~ 0.80 |
| 규모 | **255 단일 노드 run + 약 22 2노드 run, 체크포인트 13,000개 이상** |
| 명목 MTBF | 55 s → **실측 평균 간격 72.8 s** (M이 필요한 분석은 실측값 사용) |
| 장애 간격 | 지수분포 간격 + **최소 40 s** 하한 (exponential-gap renewal) |
| 분석 사용 비율 | **약 34%** |
| 지연 계측 | 애플리케이션 내부, 500 ms마다 record-weighted mean |

**제외 기준 4가지** (반드시 다 쓰세요):
(i) 주기가 체크포인트 소요의 2배보다 짧은 run (ii) 처리량이 입력을 못 따라가는 run
(iii) 정상 회복하지 못한 run (iv) 측정 창 내 복구가 안 끝난 censored episode

### B. Structural Validation ★ 핵심

| 항목 | 값 |
|---|---|
| 기하식 | `A_geo = μ_d·λ·p² / (2(μ_d − λ))` — **식 (10)** |
| 기준 조건 | 100k key·ρ=0.50, **에피소드 30개**, **R²=0.996, 기울기 1.107** |
| 두 번째 | 200k key·ρ≈0.30, **에피소드 61개**, **R²=0.982, 기울기 1.092** |
| Figure 3 모집단 | **218 에피소드** (100k **31** / 200k **168** / 400k **19**) |
| 전체 중앙 배율 | 실측이 기하식의 **약 1.21배** → 기하식이 크기를 **약 20% 낮게** 봄 |
| 범위 | 약 **네 자릿수**(10⁰–10⁴ M record·s) |

|---|---|

## ③ 지켜야 할 한정 — **이 절의 생명입니다**

| # | 반드시 | 없으면 |
|---|---|---|
| 1 | **structural validation ≠ out-of-sample prediction** (p를 같은 에피소드에서 잼) | R²=0.996이 예측 정확도로 오해됨 |
| 2 | **R²는 기울기·절편을 적합한 회귀의 값.** parameter-free인 것은 **기하식** | "R²도 parameter-free냐"는 반문 |
| 3 | **Table IV의 D·2d는 τ\* 분석 장애 run에서, Table III의 d는 무장애 run에서** 측정 | 2×3.08=6.16인데 표에는 2.9 → **설명 없는 모순** |
| 4 | **100 MB fast는 δ(d=3.08 s)와 최적점(d=1.45 s)이 서로 다른 저장소 상태에서 측정됨** | 유일하게 "맞았다"는 조건의 근거가 과대평가됨 |
| 5 | **2d는 Flink의 물리적 하한이 아니라 경험적 분석 임계값** | "그 주기가 불가능하다"로 오독 |
| 6 | **SLC 캐시 소진은 가능한 설명이나 독립 검증되지 않음** | 확정 원인처럼 읽힘 |
| 7 | **2노드는 topology와 storage가 함께 바뀜 + 1노드 비교값은 드리프트 후반(d=8–9 s)** | network distance 인과로 오독 |
| 8 | **held-out은 검증 데이터 수집 "전에" 중단** | 결과 보고 설계 바꾼 것으로 의심받음 |
| 9 | 100 MB fast 최소점은 **스윕의 왼쪽 끝** → 오른쪽 가지만 관측 | 최적점을 찾았다고 오독 |
