## 1단계: 왜 이 모델인가

**목적함수 선택** — 세 후보 중:
- 낭비 작업량(배치식) → 우리가 반박 대상
- utilization(Jayasekara) → 선행연구가 이미 함
- **record-weighted latency(우리)** → SLA가 재는 것, 계측이 직접 주는 것

**핵심 가정**: durable 소스(Kafka) → 되감기 → 재처리가 남는 용량(μ_d−λ)으로만
→ backlog 삼각형 → 비용이 checkpoint age의 **제곱**.

> 이 제곱 구조가 논문의 심장. 외부감사에서 재유도해도 맞음(통과).

## 2단계: 단일노드 실험 (255런)

### 왜 합성 워크로드인가
상태 크기와 μ를 **독립적으로** 조절해야 함 (표준 벤치마크로는 불가).
- spin으로 μ 고정(≈110k rec/s)
- 키 개수로 상태 크기 조절 (payload로 키우면 쓰기 대역 붕괴)
- payload는 의사난수 (0이면 RocksDB 압축에 먹힘)

### 스윕 구성 (m1~m12)
| 배치 | 목적 | 결과 |
|---|---|---|
| m1 | 첫 시도 | 폐기 (payload 압축 함정) |
| m2 | 기준 arm | ✅ δ, ℓ₀ 기준선 |
| m3 | 상태 스케일링 | △ k400/800 무장애도 불안정 = 안정한계 증거 |
| m4 | 해상도 향상 | ❌ τ격자가 포화하한 아래 (교훈) |
| m5 | 일반성 | RocksDB 쓰기증폭 2.5배 발견 |
| m6 | δ 재측정 | 대조런이 드리프트 검출 |
| m8 | δ vs 상태 | △ 2점 (ρ=0.30, **여기 ρ버그 있었음**) |
| m9~m12 | 가동률·held-out | 부분 |

### 진행 중 3번 방법론 수정
1. payload 압축 → 의사난수
2. τ격자를 포화하한에 맞춤 + 대조런 삽입 (m4 이후)
3. 저장소 드리프트 → 처리량 조건별 분리 적합

## 3단계: 2노드 실험 (분산 검증)

### 왜 필요했나
단일노드는 "분산"이 아님. 심사자 "이거 분산 맞아?" 방어용.

### 구성
- cluster04(JobManager+Kafka+TM), cluster03(TM+MinIO)
- 체크포인트를 cluster03 MinIO(S3)에 저장 → 복구 시 네트워크 전송
- 두 노드 TM 번갈아 kill

### 결과
- **엔진 복원 1.2s → 2.34s** (2배)
- δ는 오히려 감소 (저장소 분산)

### ⚠️ 외부감사 confound (§6 한계에 필수)
1노드→2노드에서 **두 가지 동시 변경**: 토폴로지 + 저장소(로컬→MinIO).
→ "network distance 때문"이라고 단정 못 함. "distributed+remote-storage에서
복원 증가"까지만.

### ⚠️ 클럭 오차
두 노드 ~0.1s skew 실측. D(20s)엔 무해, 서브초 δ엔 영향. 한계 명시.
