## 초록

Apache Flink과 같은 상태 기반 분산 스트림 처리 시스템은 장애 발생 시 정확한
상태 복구를 위해 주기적으로 체크포인트를 생성한다. 체크포인트 주기가 짧으면
정상 처리 오버헤드가 커지고, 길면 장애 후 재처리해야 할 데이터가 많아져 복구
지연이 증가한다. 기존의 스트림 체크포인트 주기 연구는 주로 시스템 활용률
(utilization)이나 처리 효율을 기준으로 최적 주기를 결정해 왔다. 그러나 지연
민감형 응용에서는 개별 레코드가 실제로 경험하는 지연을 직접 최소화하는 목적함수가
필요하다.

본 연구는 Kafka와 같은 durable source를 사용하는 환경에서 장애 후 발생하는 replay
backlog에 주목한다. 장애 시 마지막 체크포인트 이후의 데이터와 장애 중 유입된
데이터가 함께 누적되고, 복구 이후에도 실시간 입력이 계속되므로 backlog는 전체
처리 용량이 아닌 잔여 처리 용량으로만 감소한다. 이를 바탕으로 장애 비용을 레코드
가중 지연의 면적으로 표현하면 체크포인트 경과 시간의 제곱에 비례함을 유도하였고,
정상 체크포인트 비용과 결합하여 지연 최소화 관점의 최적 주기를 도출하였다. 그
결과 지연 최적 주기는 장애 간격에 대해 용량 손실을 기준으로 한 √M 계열 기준식보다
느리게 증가하며(국소 지수 약 0.43~0.35), 장애가 드물수록 두 방식의 차이가 커진다.

Apache Flink 1.20.5와 Kafka 3.9.2 환경에서 단일 노드 255회 실험과 2노드 분산
실험을 수행하였다. 각 장애의 입력률, 복구 중 처리율, 최대 지연만으로 자유
파라미터 없이 장애 지연 면적을 예측한 결과 대표 조건에서 R²=0.996을 확인하였다.
또한 단일 노드 로컬 저장소에서 지연 관점의 등가 체크포인트 비용은 체크포인트
수행 시간의 약 0.43~0.61배였으나, 2노드 원격 저장소에서는 0.18~0.23으로 감소하여
체크포인트 비용이 배포 구조에 따라 달라질 수 있음을 보였다.

**주요어**: 분산 스트림 처리, Apache Flink, 체크포인트, 장애 복구, Kafka, 지연 최적화

## 1. 서론

실시간 로그 분석, 금융 거래 처리, IoT 모니터링, 온라인 추천 등에서는 지속적으로
도착하는 데이터를 낮은 지연으로 처리하는 것이 중요하다. Apache Flink와 같은 상태
기반 분산 스트림 처리 시스템은 연산자 상태와 입력 진행 위치를 체크포인트에 저장하여
장애 후 일관된 상태로 복구한다. 이는 exactly-once 보장에 필수적이지만, 체크포인트
자체가 저장장치와 CPU 자원을 소비하므로 적절한 생성 주기를 결정해야 한다.

체크포인트 주기 τ가 짧을수록 장애 후 되돌아갈 구간은 줄지만 정상 처리 성능이
저하된다. 반대로 τ가 길면 정상 오버헤드는 줄지만 장애 직전 체크포인트가 오래되어
복구할 데이터가 많아진다. 따라서 주기 선택은 정상 비용과 복구 비용 사이의 전형적인
trade-off이다.

Young과 Daly의 고전 연구는 checkpoint/restart 환경에서 체크포인트 비용과 재계산량의
균형으로 최적 주기를 분석하였다[1][2]. 이후 분산 스트림 환경을 위한 연구도
수행되었다. Zhuang 등은 실시간 입력량에 따라 복구 workload가 달라지는 스트림 처리
특성을 반영한 모델을 제시하였고[3], Jayasekara 등은 bounded workload를 가정하는
고전 모델과 달리 unbounded 스트림의 활용률을 최대화하는 주기 모델을 제시하였다[4].
Zhang 등은 Flink에서 workload intensity에 따른 tuple latency와 복구 시간을 모델링해
최적 주기를 분석하였다[5].

따라서 본 연구의 목적은 스트림 체크포인트 주기를 처음 다룬다거나 기존 연구가 지연을
고려하지 않았다고 주장하는 것이 아니다. 본 연구는 **주기를 결정하는 목적함수 자체**에
초점을 둔다. 기존에 주로 다룬 활용률·처리 효율과 달리, 지연 민감형 응용에서는 장애를
경험한 각 레코드가 얼마나 오래 지연되는지가 중요하다.

특히 Kafka와 같은 durable log를 입력으로 쓰면 장애 후 데이터가 사라지지 않고 마지막
체크포인트 이후 위치로 돌아가 다시 처리된다. 이때 복구 대상 데이터만이 아니라 새로운
실시간 입력도 계속 유입되므로, replay backlog는 전체 처리 능력이 아니라 실시간 입력을
처리하고 남은 잔여 용량(μ_d−λ)으로만 감소한다. 본 연구는 이 과정을 명시적으로
모델링하여 다음을 기여한다.

1. durable replay 환경에서 backlog 감소 과정을 레코드 가중 지연 면적으로 모델링하고,
   장애 비용이 체크포인트 경과 시간의 **제곱**에 비례함을 유도한다.
2. 정상 체크포인트 비용과 replay 비용을 하나의 지연 목적함수로 결합해 최적 주기를
   유도하고, 용량 손실 기준의 √M 스케일링과 다른 스케일링을 보인다.
3. Flink/Kafka 실험에서 각 항을 독립 측정하고, 자유 파라미터 없이 장애 비용을 예측해
   모델의 기하 구조를 검증한다(R²=0.996).
4. 단일 노드뿐 아니라 2노드 분산·원격 저장소 환경에서 배포 구조가 비용에 미치는 영향을
   분석한다.

## 2. 관련 연구

### 2.1 고전 체크포인트 주기 모델

Young은 재계산 비용과 체크포인트 비용의 균형으로 최적 주기를 근사하였고[1], Daly는
이를 고차로 확장하였다[2]. 이들도 장애 후 마지막 체크포인트로 rollback하여 재수행한다.
따라서 고전과 스트림의 차이를 "배치는 저장만 하고 스트림만 되감는다"로 구분하는 것은
정확하지 않다. 보다 본질적인 차이는 스트림이 종료되지 않는 unbounded 연산이며, **복구
중에도 새 데이터가 계속 유입**된다는 점이다.

### 2.2 스트림 처리용 체크포인트 최적화

Zhuang 등은 전통적 OCI 모델이 복구 시간을 마지막 체크포인트 이후 실행시간으로만
보아 스트림에 부적합하며, 복구가 실시간 입력·재처리 workload에 의존함을 지적하였다[3].
Jayasekara 등은 분산 스트림의 활용률을 최대화하는 주기를 모델링하고 Flink에서
검증하였으며[4], 후속 연구에서 latency·throughput 변화도 평가하였다[6]. Zhang 등은
Flink에서 tuple latency와 복구 시간을 추정해 최적 주기를 계산하였다[5].

본 연구는 이들을 기반으로 하되, **continuous arrival이 존재할 때 replay backlog가
감소하는 기하를 명시적으로 유도**하고, 그로부터 record-weighted latency를 직접
목적함수로 구성한다는 점에서 접근이 다르다. **표 1**은 목적함수 관점의 차이를 요약한다.

**[표 1] 관련 연구와 본 연구의 목적함수 비교**

| 연구 | 목적함수 | 검증 | 본 연구와의 차이 |
|---|---|---|---|
| Young[1]/Daly[2] | 낭비 작업/체크포인트 비용 | 이론 | 유한 연산, 복구 중 입력 유입 없음 |
| Zhuang[3] | 처리 효율 | — | 재처리의 입력 의존 지적 |
| Jayasekara[4,6] | 활용률(utilization) | Flink | 우리는 record latency |
| Zhang[5] | tuple latency 추정 | Flink | 우리는 backlog 기하 유도 |
| **본 연구** | **record latency 면적** | **무보정 R²=0.996** | quadratic 구조 유도·검증 |

## 3. 지연 기반 체크포인트 모델

### 3.1 시스템 모델

기호: λ(입력률), μ(최대 처리율), ρ=λ/μ(가동률), τ(주기), a(장애 시 마지막 체크포인트
경과), D(실효 공백), μ_d(복구 중 처리율), M(평균 장애 간격), δ(지연 등가 체크포인트 비용).

장애 시 마지막 체크포인트 나이가 a, 처리 공백이 D이면 복구 직후 재처리 대상은 대략
`B₀ = λ(a+D)`이다. 복구 후에도 새 데이터가 λ로 유입되므로 backlog 감소 속도는 전체
처리율이 아니라 `μ_d − λ`이고, 제거 시간은 다음과 같다.

```
T_c = λ(a+D) / (μ_d − λ)
```

### 3.2 장애에 의한 레코드 지연 비용

복구 직후 가장 오래된 레코드는 약 (a+D)의 지연을 겪고, backlog가 선형 감소하면 지연도
선형으로 줄어 지연-시간 영역은 **삼각형**이 된다. 이 기간 레코드는 μ_d로 처리되므로
초과 지연의 합은

```
A = μ_d · ½(a+D) · T_c = μ_d·λ·(a+D)² / (2(μ_d − λ))
```

핵심은 장애 비용이 (a+D)에 선형이 아니라 **제곱**으로 증가한다는 점이다. 체크포인트가
오래될수록 재처리량이 늘 뿐 아니라 그 backlog를 제거하는 시간도 함께 길어지기 때문이다.
**그림 1**은 실제 장애 한 건의 지연·처리량 시계열로, 이 삼각형 구조를 보여준다.

**[그림 1] `figs/fig0_trace`** — 단일 장애 에피소드의 지연·처리량 시계열. 장애 후 지연이
급증했다 삼각형으로 감소하며, 그 면적이 (a+D)의 제곱에 비례한다.

### 3.3 평균 지연 목적함수

장애가 체크포인트 일정과 독립이면 a~U(0,τ)이므로 `E[(a+D)²] = τ²/3 + τD + D²`이다.
정상 상태 체크포인트에 의한 평균 지연 증가를 `δ²/(2(1−ρ)τ)`로 두면 전체 평균 지연은

```
L̄(τ) = ℓ₀ + δ²/(2(1−ρ)τ) + [μ_d/(2(μ_d−λ)M)]·(τ²/3 + τD + D²)
```

첫 가변 항은 τ 증가 시 감소, 둘째 항은 증가하므로 내부 최적점이 존재한다. 미분하여
0으로 두면 (ρ_d = λ/μ_d)

```
δ²·M·(1−ρ_d)/(1−ρ) = τ²·(2τ/3 + D)
```

D ≪ τ이면 `τ* ≈ (1.5·δ²M)^(1/3)`으로, 지연 최적 주기는 M에 대해 대략 세제곱근으로
증가한다(점근값). 비교를 위해 용량 손실(capacity/wasted-work)을 기준으로 한 baseline을
`τ*_cap ≈ √(2δ_cap·M/ρ)` 형태로 두면 √M에 비례한다. 이 baseline은 본 모델의 용량 회계로
구성한 참조선이며 Jayasekara[4]의 정확한 활용률 최적값과는 다르다. 따라서 동일 시스템이라도
용량 기준 주기와 지연 기준 주기는 서로 다른 값을 택할 수 있다.

### 3.4 평균 부하 안정 조건

장애 backlog를 지속적으로 제거하지 못하면 지연이 누적된다. 평균 경과를 τ/2로 두면
예상 catch-up 시간으로부터 다음 조건을 얻는다.

```
λ(τ/2 + D)/(μ_d − λ) + D < M
```

이는 deterministic hard bound가 아니라 first-moment 기반 평균 부하 안정 조건이다. 실제
장애 간격은 확률적이므로 개별 장애가 항상 이를 만족한다고 보장할 수는 없다.

## 4. 실험 환경 및 방법

### 4.1 실험 환경

단일 노드 실험은 Intel i9-9900K(16스레드) 서버에서 수행하였다. Apache Flink 1.20.5를
standalone으로, Kafka 3.9.2를 KRaft 모드로 실행하고 RocksDB 상태 백엔드에 full,
exactly-once, aligned 체크포인트를 적용하였다. 단일 노드 캠페인은 총 255회, 체크포인트
13,000회 이상이었다. 분산 영향을 확인하기 위해 동일 계열 두 서버로 2노드 실험을
추가하였다. 2노드에서는 첫 노드에 JobManager·Kafka·일부 TaskManager를, 둘째 노드에
TaskManager와 MinIO를 배치하고 체크포인트를 S3 호환 원격 저장소에 기록하였다.

### 4.2 합성 workload

상태 크기와 처리율을 독립 조절하기 위해 합성 workload를 사용하였다. 레코드당 CPU
부하는 spin loop로, 상태 크기는 payload가 아니라 key 개수로 조절하였다. 초기에는
0으로 채운 payload를 썼으나 RocksDB 압축으로 실제 체크포인트 크기가 작아지는 문제가
있어 이후 키 기반 의사난수 데이터를 사용하였다. 상태 크기는 약 100·200·400 MB로,
기준 가동률은 ρ=0.5로 두었다(일부 ρ=0.3, 0.65, 0.8).

### 4.3 지연 및 처리율 계측

Flink의 장기 평균 metric은 초 단위 동역학 포착이 어려워 애플리케이션 내부에서 직접
측정하였다. 각 레코드에 생성 시각을 포함해 처리 시점의 시각차를 계산하고, 500ms마다
처리 레코드 수와 지연 통계를 기록하였다. 평균 지연은 시간 평균이 아니라 처리 레코드
수를 가중치로 한 record-weighted mean을 사용하였다. 각 장애 에피소드에 대해 마지막
체크포인트 나이 a, 복원 시간, 최대 지연, 복구 중 처리율 μ_d, 정상 회복까지의 초과
지연 면적을 측정하였다.

### 4.4 장애 주입

TaskManager를 강제 종료 후 재기동하는 방식으로 장애를 주입하였다. 장애 간격은 단순
Poisson이 아니라 지수분포 간격에 최소 40초 하한을 적용한 exponential-gap renewal
process로 생성하여 복구 에피소드 간 중첩을 줄였다. 명목 MTBF는 55초였으나 실제 주입된
평균 간격은 약 **72.8초**였으며, M이 필요한 분석에서는 실측 간격을 사용한다.

### 4.5 데이터 제외 기준

장시간 실험 중 체크포인트 쓰기 처리량이 약 288 MB/s에서 63 MB/s로 감소하는 현상이
관찰되었다(그림 4). 서로 다른 시간대의 run을 결합하면 주기 효과와 storage drift를
구분하기 어려우므로, 주기 실행 순서를 무작위화하고 동일 조건의 control run을 주기적으로
삽입하였다. 또한 (i) 주기가 체크포인트 소요의 2배보다 짧은 run, (ii) 처리량이 입력을
못 따라가는 run, (iii) 정상 회복하지 못한 run, (iv) 체크포인트 수가 과소한 run,
(v) 측정 창 내 복구가 끝나지 않은 censored episode를 구분하였다. 여기서 τ<2d 기준은
물리적 최소 주기가 아니라 1/τ 정상상태 회귀를 안정적으로 측정하기 위한 경험적 분석
임계값이다.

## 5. 실험 결과

### 5.1 장애 지연 비용의 검증

가장 중요한 검증은 이론식이 개별 장애의 누적 지연 면적을 설명하는지 확인하는 것이다.
각 장애에서 입력률 λ, 복구 중 처리율 μ_d, 최대 지연 p를 직접 측정해 `A_pred =
μ_d·λ·p²/(2(μ_d−λ))`를 계산하였다. 즉 모델에 맞추기 위한 자유 파라미터를 추가하지
않고 관측값만 사용하였다.

100k key 조건 30개 에피소드에서 예측과 측정의 결정계수는 **R²=0.996**, 200k key·ρ≈0.3
조건 61개 에피소드에서 **R²=0.982**였다(**표 2**, **그림 2**). 본 검증은 별도의 자유
파라미터를 데이터에 적합하지 않으므로, 회귀 파라미터 적합에 따른 과적합 가능성을 줄이고
예측식의 기하학적 관계 자체를 평가할 수 있다. 다만 episode 제외 기준, μ_d 측정 방식,
최대 지연의 정의와 같은 분석 선택은 여전히 존재하며 이는 §6에서 논의한다.

**[표 2] 무보정 장애 비용 예측**

| 조건 | 에피소드 | R² | 기울기/예측 |
|---|---|---|---|
| 100k key, ρ=0.50 | 30 | **0.996** | 1.107 |
| 200k key, ρ=0.30 | 61 | **0.982** | 1.092 |

**[그림 2] `figs/fig3_area_validation`** — 자유 파라미터 없는 장애 비용 예측. 측정한
λ, μ_d, 최대 지연만으로 계산한 예측(x)과 실측 초과 지연 면적(y). 세 상태 크기에 걸쳐
2자릿수 범위에서 y=x를 따른다.

### 5.2 체크포인트의 두 가지 비용

체크포인트 중 손실 처리 용량으로 계산한 값과 정상 지연 곡선에서 추정한 등가 지연 비용
δ는 크게 달랐다. 용량 관점은 약 0.15~0.22초였으나 지연 관점 δ는 약 1.37~4.16초로,
조건에 따라 **8.8~18.6배** 차이였다. 이는 체크포인트가 모든 연산을 정지시키지 않아도
barrier, 상태 스냅샷, 순간 지연으로 많은 레코드의 지연을 늘리기 때문이다. 따라서 용량
감소만을 비용으로 쓰면 지연 민감형 workload에서 실제 체감 비용을 과소평가한다.

### 5.3 체크포인트 수행 시간과 δ

단일 노드 로컬 저장소 네 조건에서 지연 관점 δ와 체크포인트 소요 d의 비율은 0.43~0.61
범위였다(**표 3**). 따라서 해당 환경에서는 δ≈d/2를 초기 추정으로 쓸 여지가 있다. 그러나
이를 일반 법칙으로 볼 수는 없다. 2노드 원격 저장소에서는 δ/d가 0.18~0.23으로 감소하여,
체크포인트 소요만으로 지연 등가 비용을 일반적으로 결정하기 어렵고 저장소·배포 구조에
따라 비율이 달라짐을 보였다.

**[표 3] 조건별 체크포인트 비용 δ (ρ버그 수정 반영)**

| 상태 | 저장소 | ρ | δ (s) | d (s) | δ/d |
|---|---|---|---|---|---|
| 100 MB | 빠름 | 0.50 | 1.371 | 3.08 | 0.45 |
| 200 MB | 빠름 | 0.50 | 1.907 | 3.12 | 0.61 |
| 100 MB | 느림 | 0.30 | 3.195 | 5.24 | 0.61 |
| 200 MB | 느림 | 0.30 | 4.159 | 9.67 | 0.43 |
| 2노드 | 원격 | 0.50 | — | — | 0.18~0.23 |

### 5.4 목적함수에 따른 최적 주기의 차이

유도한 모델(기준 arm δ=1.907s, D=4.28s, ρ=0.5)로 지연 최적 주기와 용량/낭비
기준(capacity/wasted-work baseline) 주기를 비교하였다(**표 4**, **그림 3**). 장애 간격이
커질수록 두 방식의 차이가 증가한다. 용량/낭비 기준은 대략 τ*∝√M이나, 지연 모델은 국소
지수가 M=55s에서 약 0.43, M=1일에서 약 0.35로 나타나 √M보다 느리게 증가한다(1/3 점근).
따라서 장애가 드문 환경일수록 용량/낭비 기준으로 택한 긴 주기가 지연 민감형 응용에는
과도하게 길 수 있다.

**[표 4] 목적함수별 최적 주기(모델 계산, 기준 arm)**

| M | 지연 최적 τ* | 용량/낭비 기준 τ*(√M) | 비율 |
|---|---|---|---|
| 30 s | 3.8 s | 5.1 s | 1.4배 |
| 55 s | 4.9 s | 7.0 s | 1.4배 |
| 10분 | 12.4 s | 23.0 s | 1.8배 |
| 1시간 | 24.0 s | 56.2 s | 2.3배 |
| 1일 | 72.7 s | 275.5 s | 3.8배 |

*용량/낭비 기준 열은 본 모델의 wasted-work 회계 τ*=√(2δ_cap·M/ρ)로 계산한 참조선이며,
문헌[4]의 정확한 활용률(utilization) 최적값이 아니다. 직접 비교하려면 해당 논문의 수식으로
별도 계산이 필요하다. 지연 열의 1/3은 D≪τ 점근값이다.*

**[그림 3] `figs/fig2_scaling`** — 목적함수별 최적 주기의 M 의존성. 낭비 기준은 √M,
지연 기준은 더 느리게(국소 0.43→1/3) 증가한다. 음영은 평균 부하 안정 조건을 넘어 복구가
지속 불가능한 영역.

### 5.5 저장소 성능 변화의 영향

장시간 실험 중 동일 서버의 체크포인트 쓰기 처리량이 약 4배 이상 변화하였다. 초기
200 MB/s 이상에서 이후 60~70 MB/s까지 감소해 동일 상태에서도 체크포인트 소요가 2~3초에서
8~10초로 늘었다(**그림 4**). `iostat` 확인 결과 장치 사용률 90.6%, 요청당 14.7ms로 포화
상태였다. 주기를 작은 값부터 큰 값 순으로 실행하면 이 열화가 τ 변화와 같은 방향으로
나타나 두 효과가 혼동되므로, 이후 실험에서 순서를 무작위화하고 고정 주기 control run을
배치하였다. 이는 체크포인트 연구에서 저장소 처리량을 상수로 가정하면 잘못된 회귀 결과를
얻을 수 있음을 보여준다.

**[그림 4] `figs/fig5_storage_drift`** — 31시간 연속 실험 중 체크포인트 쓰기 처리량 변화.
약 288 MB/s에서 63 MB/s로 감소 후 안정.

### 5.6 평균 부하 안정성

일부 조건에서 주기가 길수록 장애 backlog를 다음 장애 전에 제거하지 못해 지연이 누적되는
현상이 관찰되었다. 대표 실험에서 τ=64초까지는 정상 회복하였으나 τ=128초에서는 회복하지
못하는 run이 나타났다. 또한 큰 상태에서는 장애가 없어도 잦은 체크포인트가 처리 용량을
감소시켜 입력을 못 따라가는 현상이 관찰되었다. 이는 주기 최적화가 단순 최솟값 탐색이
아니라, 먼저 시스템이 안정적으로 동작하는 영역 내에서 수행되어야 함을 의미한다.

### 5.7 2노드 분산 환경

단일 노드로는 분산 배치 영향을 관찰하기 어려워 2노드 Flink 환경을 구성하였다. 단일
노드는 로컬 파일시스템을, 2노드는 둘째 서버의 MinIO(S3 호환) 원격 저장소를 체크포인트
저장소로 사용하였다. 이 조건에서 Flink가 보고한 엔진 복원 시간은 약 **1.2초에서 2.39초로
증가**하였다(**표 5**). 반면 체크포인트 δ는 감소하였는데, 두 노드에서 쓰기가 분산되는
효과와 관련될 수 있다. 즉 분산화는 D와 δ를 같은 방향이 아니라 상반된 방향으로 변화시킬
수 있다.

다만 단일 노드와 2노드 비교에서는 노드 topology와 체크포인트 저장소 backend가 동시에
변경되었으므로 복원 시간 증가를 network distance만의 인과로 해석할 수 없다. 또한 두 노드
사이 약 0.1초의 clock offset이 관찰되어, 수십 초 규모의 복원 시간에는 영향이 제한적이나
수백 ms 규모의 δ 비교에서는 오차가 무시되지 않는다. 따라서 본 결과는 **분산 배치와 원격
저장소를 함께 사용한 구성에서 복구 시간이 증가하였다**로 제한적으로 해석한다.

**[표 5] 단일 노드 대 2노드 분산**

| 지표 | 1노드 | 2노드 | 변화 |
|---|---|---|---|
| 엔진 복원 시간 | 1.20 s | 2.39 s | ×2.0 |
| δ/d | 0.43~0.61 | 0.18~0.23 | 감소 |
| 클럭 오차 | — | ~0.1 s | (한계) |

## 6. 한계 및 논의

첫째, workload가 실제 서비스가 아닌 synthetic이다. 상태 크기와 처리량을 독립 조절하기
위해 단순화하였으므로, 복잡한 join·window·비동기 I/O·외부 sink 환경에서는 파라미터가
달라질 수 있다. 둘째, 장애 유형은 TaskManager 강제 종료 중심이며 네트워크 단절, 디스크
장애, JobManager 장애에서는 복구 구조가 다를 수 있다. 셋째, 2노드 실험에서 topology와
저장소가 동시 변경되어 두 효과를 분리할 수 없다. 넷째, 두 노드 간 약 0.1초 clock offset이
있어 수백 ms 수준의 지연 비교에는 오차가 있다. 다섯째, δ/d=0.43~0.61은 로컬 저장소의
경험적 결과일 뿐 일반 상수가 아니며 2노드에서 0.18~0.23으로 감소한다. 마지막으로 안정
조건은 확률적 안정성 증명이 아니라 first-moment 근사이다.

그럼에도 핵심 backlog-latency 관계는 서로 다른 조건에서 높은 설명력을 보였으며, 이는
체크포인트 주기를 활용률 문제로만이 아니라 사용자 체감 지연 관점에서도 분석할 필요가
있음을 보여준다.

## 7. 결론

본 연구는 durable source를 사용하는 분산 스트림 처리에서 체크포인트 주기를 record-weighted
latency 관점으로 분석하였다. 장애 후 replay 시 새 입력이 계속 유입되므로 backlog는 잔여
용량 μ_d−λ로만 감소하며, 이로부터 장애 비용이 (a+D)²에 비례함을 유도하였다. 이를 정상
체크포인트 비용과 결합하면 용량 손실 기준(√M)과 다른 최적 주기가 도출되며, 일정 조건에서
지연 최적 주기는 √M보다 느리게(국소 0.43~0.35) 증가한다. Flink/Kafka 실험에서 개별 장애 측정값만으로
계산한 지연 비용이 실측을 대표 조건에서 R²=0.996으로 설명하였고, 체크포인트의 지연 등가
비용이 단순 용량 손실보다 크며 배포·저장소 구조에 따라 비용이 상반되게 변할 수 있음을
확인하였다. 향후 로컬/원격 저장소를 독립 변경하는 실험, 더 많은 노드, 실제 workload, 다양한
장애 유형으로 일반성을 검증할 계획이다.

본 연구의 원자료(255회 실험, 13,000회 이상 체크포인트)와 분석 스크립트를 공개하며,
논문의 수치는 검증 스크립트로 원자료에서 재확인할 수 있다.
