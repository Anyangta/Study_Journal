## 1단계 — 준비 (09-06, 착수 ~ 16:15)

### v0.0.0 착수
- 주제 확정: 스트리밍 체크포인트 주기
- 문제 인식: 고전 공식(Young/Daly)의 두 가정이 durable log 환경에서 깨진다

### v0.1.0 실험 환경 구축 + 모델 유도
- cluster04에 Flink 1.20.5 + Kafka 3.9.2(KRaft) 구성
  — **sudo·docker 권한이 없어** 전부 홈 디렉터리 사용자 프로세스로
- 측정 대상 잡(`CkptJob.java`), 정속 생성기(`EventGen.java`) 작성
- 모델 유도: 장애 항이 2차가 되는 이유, 안정 한계 식

**여기서 걸린 함정 3개**
1. `EventGen`이 slf4j 없음으로 죽음 → 클래스패스에 Kafka libs 전체 필요
2. 잡 파라미터가 TaskManager에 전달 안 됨 → `JVM_ARGS`로 넘겨야 함
3. 백그라운드 실행이 호출자를 블로킹 → `setsid nohup … < /dev/null &`

### v0.2.0 캘리브레이션
- 백로그 배수 속도로 `mu` 측정 (추정이 아니라 실측)
- **payload 4 KB에서 `mu`가 513 rec/s로 붕괴** — 쓰기 대역이 터짐
  → 상태 크기는 **키 개수**로 조절하기로 결정
- **상태가 압축돼 사라지는 문제 발견**: 200 MB 설정이 체크포인트에 36 MB로 기록
  → payload를 키 유래 의사난수로 채움. 534~701 MB, 소요 2.1~2.8초로 정상화

### v0.2.1 계측 정밀화
- **Flink 메트릭이 60초 이동평균**이라 체크포인트(2초)·재시작(4초)을 못 잡음
  → 잡 안에서 500 ms 주기로 직접 계측하도록 재작성
- **고정 60초 제외 창이 표본을 통째로 날림** (장애 간격이 55초라서)
  → 에피소드별 실측 복구 시간 기반 2-패스로 변경

## 5단계 — 두 번째 오염 발견 (09-07 20:15 ~ 23:30)

### v0.5.0 드리프트의 진짜 정체는 공용 서버의 일주기 경합

**증상**: 재실행 데이터로 `verify.py`가 **30개 중 9개만 통과.**
기준 arm 정상 적합 R² 0.008, 면적 적합 R² −0.004.

**먼저 배제한 것**: `local_state_mb_at_end`가 2~3 GB로 일정하고 `rocksdb/`도
2.0 GB뿐. 디스크 20%. **우리 쪽 누적은 재발하지 않음.**

**진짜 원인**: JobManager 로그에서 체크포인트 **6127개**를 파싱해 시간대별 쓰기
처리량 측정 →

|---|---|---|---|
| 02시 | 359 MB | 1.42 s | **250 MB/s** |
| 03시 | 858 MB | 3.25 s | **268 MB/s** |
| 09시 | 406 MB | 2.63 s | 138 MB/s |
| 14시 | 542 MB | 6.91 s | 78 MB/s |
| 17시 | 542 MB | 8.13 s | **66 MB/s** |

**크기는 그대로인데 처리량만 4배.** 공용 장비의 업무 시간 경합.

**두 번째 원인**: δ를 M=55s 장애 런으로 적합하고 있었음 → 무장애 런으로 바꾸니
R²가 0.008→0.863, 0.110→0.979로 회복.

**조치**
1. `drift.py` — 런별 처리량을 붙여 보고, 부분집합만으로 재적합
2. `mkcfg_drift.py` — **τ 순서 무작위화 + 고정 τ 대조런 삽입**
3. `model.py` — 정상 항은 무장애 런 우선, `n_ckpt < 5` 배제
4. `plot.py` — fig4가 ρ 범위 하드코딩이라 m8을 무시할 뻔한 것 수정
5. **m6·m8 재설계**, 조용한 시간대를 δ 측정에 배정
